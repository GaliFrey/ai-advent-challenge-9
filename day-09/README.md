# День 9. Сжатие истории через summary

Двухпанельный TUI отправляет одинаковое сообщение двум агентам с одной моделью DeepSeek. Левый агент передаёт всю историю, правый заменяет старую часть recursive summary и сохраняет последние N сообщений без изменений.

## Как устроено

```text
сообщение пользователя
├── system + полная история + сообщение → DeepSeek → ответ слева
└── system + summary + последние N + сообщение → DeepSeek → ответ справа
                                              └── обновление summary по интервалу
```

- Модель и N выбираются до первого запроса и блокируются на время сессии.
- По умолчанию справа остаются четыре последних сообщения; в финальном прогоне выбрано `N=6`.
- Интервал summary — десять новых сообщений. Сообщениями считаются отдельные элементы `user` и `assistant`, поэтому десять сообщений накапливаются за пять пользовательских ходов.
- Суммаризация выполняется после ответа правого агента. В демо summary обновляется в конце ходов 5, 10 и 15; панель показывает число сообщений до следующего обновления.
- Новое summary строится из предыдущего summary и очередного старого префикса. Старые сообщения удаляются из рабочего контекста только после успешного ответа суммаризатора.
- При ошибке исходная история остаётся доступной, ошибка фиксируется в TUI и JSON-отчёте. Автоматического сетевого повтора нет.
- Агент использует общие знания и может писать код. Только факты о пользователе, проекте и прошлых решениях берутся строго из контекста; старые требования к формату ответа не переносятся на новые запросы.
- Обе панели показывают точные значения `usage` DeepSeek. В правой отдельно учитываются рабочие запросы и суммаризатор, а в общий расход входят оба вида вызовов.
- Диалог хранится только до закрытия приложения. Постоянная память была отдельной задачей дня 7 и здесь не влияет на сравнение prompt.

В интерфейсе доступны `deepseek-v4-flash` и `deepseek-v4-pro`. Обе панели всегда используют одну выбранную модель, `temperature` и лимит ответа.

## Запуск

Требуются Python 3.11 или новее, `uv` и API-ключ DeepSeek.

```bash
cd ~/Dev/AI_Advent_Challenge/day-09
uv sync --locked
cp .env.example .env
```

Добавь `DEEPSEEK_API_KEY` в `.env` и запусти:

```bash
uv run --locked python main.py
```

`Ctrl+D` запускает демо на пустой истории, `Ctrl+Q` закрывает приложение. Summary можно полностью вывести в правую панель. Очистка обеих историй требует повторного подтверждения.

## Демо и отчёт

Кнопка `Демо · 35 API-вызовов` выполняет не 35 сообщений, а:

- 15 пользовательских ходов в обеих панелях — 30 рабочих API-вызовов;
- один контрольный вопрос в обеих панелях — ещё два рабочих вызова;
- три обновления summary — три служебных вызова.

Сценарий содержит ранний идентификатор проекта, первоначальные дату, бюджет и подрядчика, их последующую отмену, актуальные значения и открытый вопрос. Локальная проверка оценивает пять фактов без дополнительной LLM-судьи; правильные ответы в контрольный prompt не передаются.

После полного или частичного демо атомарно создаётся `day-09/results/demo-<timestamp>.json`. Отчёт содержит безопасную конфигурацию без API-ключа, запросы и ответы, события и ошибки summary, фактическое число API-попыток, токены, итоговое состояние памяти, проверки качества и экономию. Последующие ручные сообщения продолжают обновлять статистику TUI, но уже созданный снимок демо не изменяют.

## Результат автоматического демо

Финальный прогон 10.09.2026 выполнен на `deepseek-v4-flash` при `temperature=0`, `N=6` и интервале десять сообщений. Все 35 API-вызовов завершились успешно.

| Метрика | Полная история | Summary + последние N |
| --- | ---: | ---: |
| Качество контрольного ответа | 5/5 | 5/5 |
| Вход рабочих запросов | 10 510 | 9 373 |
| Выход рабочих запросов | 170 | 170 |
| Токены суммаризации | 0 | 2 218 |
| Общий расход | 10 680 | 11 761 |
| Последний prompt | 1 185 | 823 |

Сводка обновилась после ходов 5, 10 и 15; ошибок не было. К контрольному вопросу 24 сообщения были сжаты, восемь последних оставались исходными. Обе панели вернули одинаковые актуальные проект, дату, бюджет, подрядчика и открытый вопрос.

Последний prompt уменьшился на 30,5%, а рабочие запросы вместе — на 10,8%. Но суммаризатор дополнительно потратил 2 218 токенов, поэтому весь короткий прогон оказался дороже полной истории на 1 081 токен, или 10,1%. Экономия prompt появляется после сжатия, а суммарная экономия требует достаточно длинного диалога для компенсации служебных вызовов.

Исходный отчёт: [`results/demo-20260910T165005-418481Z.json`](results/demo-20260910T165005-418481Z.json).

После автоматического демо диалог продолжен обычными вопросами о Bash, работе LLM и Python. Это позволило проверить, как затраты summary окупаются на последующих запросах. Финальное состояние записи:

| Рабочие запросы | 25/25 | 25/25 |

К концу сессии сжато 44 сообщения. Последний prompt стал меньше на 34,6%, а общий расход с учётом пяти вызовов суммаризатора — на 3 224 токена, или 8,3%. Оценка 5/5 относится к контрольному вопросу автоматического демо; последующие ответы проверены визуально, но не оценивались автоматическим валидатором.

Запись проверена по шести кадрам: видны исходная конфигурация, три summary и 5/5 в демо, последующие ответы обеих панелей, summary v5 и итоговая экономия 8,3%; секреты не обнаружены. API Яндекс Диска подтвердил размер 12 588 543 байта, MIME `video/mp4`, антивирусный статус `clean` и совпадение контрольных сумм с локальным файлом.
