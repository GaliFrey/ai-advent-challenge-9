# День 32 — автоматическое ревью PR Guitar Trainer

Ревьюер запускается через GitHub Actions в отдельном репозитории
[Guitar Trainer](https://github.com/GaliFrey/guitar-trainer), читает diff и
снимки изменённых файлов, ищет контекст в документации **и коде**, отправляет
один запрос DeepSeek и сохраняет текст ревью. Канонический код ревьюера
остаётся в `day-32` репозитория челленджа. Код приложения сюда не копируется.
Оригинал задания хранится локально в `resources/task.md`. Формат сдачи —
видео + код; видео пока не записано, полная сдача ДЗ не выполнена.

## Как работает

1. Workflow реагирует на открытие/обновление/повторное открытие PR и снятие
   draft. PR из форков и draft пропускаются; ключ доступен только шагу ревью.
2. GitHub runner получает head приложения и отдельную версию ревьюера,
   закреплённую полным SHA в repository variable `AI_REVIEWER_REF`.
3. Ревьюер вычисляет merge-base между base/head из события. Diff соответствует
   изменениям ветки PR относительно общего предка, а не посторонним изменениям
   base-ветки. Переименования представлены удалением и добавлением.
4. Из Git-объектов читаются полные before/after изменённых текстовых файлов.
   Рабочая копия приложения и её незакоммиченные изменения не используются.
5. В памяти заново строится индекс head: README.md, docs/**/*.md,
   исходники `.js/.ts/.py` в src/test/scripts, index.html, styles.css и
   package.json. Не читаются .env, PLAN.md, node_modules, ресурсы и скрытые пути.
6. Для каждого изменённого файла подбираются до двух фрагментов документации
   и двух фрагментов другого кода. Семантический поиск дополняется совпадениями
   имени файла и экспортируемых API. Короткие абзацы документации раскрываются
   целиком. Повторные/перекрывающиеся контексты внутри подборки исключаются.
7. DeepSeek получает diff, список файлов, полные изменённые тексты base/head
   и выбранные RAG-фрагменты. Весь корпус не передаётся. Код PR не выполняется,
   модель не получает инструменты, команды и права изменять репозиторий.
8. Проверяется JSON-контракт: категории bug/architecture/recommendation,
   приоритеты P1–P3, изменённый путь и строка соответствующей стороны diff,
   существующие источники и точное вхождение цитат. Каждое замечание обязано
   цитировать соответствующий изменённый файл. Отклонённое ревью и ошибки API
   дают ненулевой код выхода; автоматических повторов нет.
9. `review.md` показывается в Job summary; `review.json` с точным контекстом,
   принятым ответом и статистикой сохраняется как Actions artifact на 7 дней.
   Комментарии в PR не публикуются. Наличие замечаний само по себе не делает
   job красным: статус показывает, выполнено ли ревью, а не решение о merge.

RAG использует CPU-модель
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2`, ревизия
`e8f8c211226b894fcb81acc59f3b34ba3efd5f42`. Окна до 112 токенов с
перекрытием 16, нормализованные векторы и скалярное произведение.
Алгоритм окон переиспользован из дня 21 без runtime-зависимости от него.
Индекс не сохраняется между PR: он всегда относится к текущему head.
На GitHub модель загружается из Hugging Face; для её работы Ollama не нужен.

## Установка в GitHub

1. Опубликовать код дня 32 в `GaliFrey/ai-advent-challenge-9`.
2. В Guitar Trainer создать Actions Secret `DEEPSEEK_API_KEY`.
3. В Settings → Secrets and variables → Actions → Variables создать
   `AI_REVIEWER_REF`: полный SHA опубликованного коммита ревьюера. Новые
   версии включаются явным обновлением этой переменной, не автоматически
   с каждым изменением main репозитория челленджа.
4. Скопировать `workflows/ai-review.yml` в
   `.github/workflows/ai-review.yml` приложения и закоммитить в его основную
   ветку. В workflow задан существующий публичный репозиторий челленджа;
   для другого источника нужно изменить `repository` соответствующего checkout.
5. Открыть PR из ветки Guitar Trainer. Результат доступен в Actions → AI review
   → Summary и Artifacts. Для уже открытого PR отправить новый коммит.

Workflow использует стандартный GitHub-hosted Linux runner, Python 3.12,
uv 0.12.19, `uv sync --locked`. Actions закреплены по проверенным SHA.
Права GITHUB_TOKEN ограничены `contents: read`; checkout не сохраняет
учётные данные. Установка зависимостей выполняется только для доверенного
ревьюера. Код/зависимости приложения не запускаются с API-ключом.
Инструкции по uv: https://docs.astral.sh/uv/guides/integration/github/.
Секреты/форки: https://docs.github.com/en/actions/how-tos/write-workflows/choose-what-workflows-do/use-secrets.

## Локальный запуск

Нужны Git, uv, Python 3.12+. Для `verify_local.py` нужен Node.js 22+.

```bash
cd day-32
uv sync --locked
# По необходимости создать .env из .env.example и задать свой ключ.
uv run --locked python main.py --project /path/to/guitar-trainer \
  --base FULL_BASE_SHA --head FULL_HEAD_SHA --retrieve-only
# Один платный запрос:
uv run --locked python main.py --project /path/to/guitar-trainer \
  --base FULL_BASE_SHA --head FULL_HEAD_SHA
```

Base/head — полные 40-символьные SHA коммитов, доступных в локальной истории.
Модель по умолчанию `deepseek-flash`; локально можно изменить через
`DEEPSEEK_MODEL`. Читается только `.env` самого дня 32, а не приложения.
Результаты по умолчанию записываются в игнорируемый `resources/review`.
Ключ не сохраняется в отчёте; провайдерские ошибки показываются без тела
HTTP-ответа. JSON содержит исходники, поэтому artifact нельзя считать
свободным от конфиденциальной информации лишь потому, что в нём нет ключа.

## Проверки

```bash
uv run --locked python -m unittest -v
uv run --locked python -m py_compile snapshot.py rag.py provider.py review.py main.py verify_local.py test_review.py
uv lock --check
# Реальные локальные эмбеддинги и тест-подтверждённый пример, без DeepSeek:
uv run --locked python verify_local.py --project /path/to/guitar-trainer
```

Офлайн-тесты используют настоящий Git во временных репозиториях, заменяют
эмбеддинги и API. Проверяются merge-base, независимость от рабочей копии,
новые/удалённые/переименованные файлы, пути с пробелами, symlink, секреты,
бинарные файлы, пределы размера, ссылки/цитаты/позиции, ошибки провайдера
и отсутствие повторов/LLM-вызова в retrieve-only.

`verify_local.py` создаёт временный clone, подтверждает успешный базовый
`pitch-match.test.js`, удаляет сброс `since` при неподходящем кадре и
проверяет, что тот же тест теперь завершается ошибкой. Затем выполняет
настоящий RAG и сохраняет исходный контекст/логи в `resources/local-check`.
Исходный Guitar Trainer не меняется; временный clone удаляется.

## Результаты и ограничения

Локальная проверка 13.10.2026: настоящий RAG обработал 44 документа/кодовых
файла и 1101 чанк, для демонстрационного изменения выбраны четыре контекста.
Базовый тест завершился с кодом 0, версия с ошибкой — с кодом 1.
Платных LLM-вызовов в этой проверке не было. Результаты GitHub Actions и
DeepSeek будут добавлены после фактического прогона, а не по наличию workflow.

Ограничения первой версии:

- До 20 изменённых файлов, diff до 80 КБ, изменённые тексты суммарно до
  140 КБ, отдельный файл до 250 КБ, корпус до 2 МБ/500 файлов, сериализованный
  контекст до 300 КБ. Превышение останавливает ревью без скрытого усечения.
- Бинарные/non-UTF8 изменения явно отмечаются как не прочитанные текстом.
  Symlinks/submodules в корпусе или изменениях отклоняются. Изменения
  `.env`/закрытых ключей отклоняются до передачи diff в облако; это не
  полноценный сканер секретов в произвольных исходниках.
- Удалённые строки могут получить замечание на стороне base. Изменения
  только режима/бинарных данных не имеют доступных строк для замечаний.
- Поиск ограничен явно описанным корпусом и не гарантирует нахождение всех
  зависимостей. Проверка цитат/строк не доказывает правильность вывода LLM.
- DeepSeek получает фрагменты кода. Для чужого/закрытого проекта нужно
  учитывать разрешение владельца на такую передачу.
- PR из форков и draft пропускаются. Повторное обновление PR делает новый
  платный запрос; отмена старого job не гарантирует отмену уже отправленного API-запроса.
- Отсутствие замечаний не доказывает отсутствие ошибок. Сбой API не
  представляется успешным ревью. Тесты приложения внутри job не запускаются.
- Браузерных, визуальных и микрофонных проверок в этом задании не было.
