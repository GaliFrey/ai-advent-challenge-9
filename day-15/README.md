# День 15. Контролируемые переходы состояний

Приложение реализует управляемый человеком жизненный цикл задачи. Каждое посещение рабочей стадии — отдельный сохраняемый `StageRun` с несколькими сообщениями и собственным снимком артефакта. Ответ LLM обновляет только активный запуск и текущий артефакт; фазу он не меняет.

Переход выполняется отдельным управляющим действием пользователя через единый `TransitionController`:

```text
planning ── пользователь утвердил план ──► execution
    ▲                                         │
    └──── пользователь вернул к плану ────────┘
                                              │ пользователь отправил результат
                                              ▼
                                         validation
                              ┌ failed ───────┤────── passed ──► done
                              ▼               │                  только после принятия
                           revision ──────────┘
                              пользователь отправил доработку
```

Внутри каждой фазы может быть сколько угодно модельных ходов без перехода:

```text
planning
  пользователь: составь план
  ассистент: версия 1
  пользователь: добавь отдельную проверку
  ассистент: версия 2
  пользователь нажимает «Утвердить план»
                                      └──────► execution
```

Пауза хранится отдельным статусом. После загрузки checkpoint восстанавливаются фаза, хронологический список запусков, их диалоги и артефакты, а также ожидаемое действие.

## Граница ответственности

- LLM обсуждает и формирует содержимое текущей стадии: план, результат выполнения, отчёт проверки или исправленную версию.
- Пользователь решает, когда артефакт готов к следующей стадии.
- Код определяет допустимые фазы, события, переходы и предусловия.
- Обычное сообщение в чате никогда не считается командой перехода.
- Модель не возвращает и не назначает `next_state`.
- Просьба «игнорируй стадии и сразу выдай финал» остаётся сообщением внутри текущей сессии и не способна изменить фазу.
- Разрешённый переход только создаёт новую пустую сессию стадии. Пользователь сам отправляет первый запрос в execution, validation или revision; переход не вызывает LLM автоматически.

Все стадии используют JSON mode для разделения пользовательского ответа и полного актуального артефакта. Техническая ошибка ответа не продвигает checkpoint и не добавляет незавершённую пару в историю стадии.

## Запуски стадий

В `TaskState.runs` хранится хронологический маршрут:

```text
StageRun(phase="planning", visit=1)
StageRun(phase="execution", visit=1)
StageRun(phase="validation", visit=1)
StageRun(phase="revision", visit=1)
StageRun(phase="validation", visit=2)
```

Каждый возврат создаёт новый запуск, в том числе `planning #2`, `execution #2` или `validation #2`. Новый запуск получает только необходимые формализованные артефакты:

- новый planning — исходную цель и текущую версию плана;
- новый execution — цель и заново утверждённый план;
- новая validation — цель, утверждённый план и актуальный результат;
- revision — результат и замечания последней validation.

Диалоги предыдущих запусков в новые prompts не копируются. Поэтому `validation #2` не получает разговор из `validation #1` и оценивает исправленный результат заново, а `planning #2` не наследует длинный planning-чат первого посещения. Старые запуски остаются неизменяемой историей для просмотра и аудита. В интерфейсе между ними можно перемещаться стрелками; писать разрешено только в последний активный запуск.

## Разрешённые и запрещённые маршруты

Разрешённые переходы находятся в таблице `TRANSITIONS`; за пределами контроллера прямых присваиваний новой фазы нет. Для каждого ребра проверяется содержательное предусловие:

- `planning → execution` требует сформированного плана и завершённой пары сообщений planning;
- `execution → validation` требует результата выполнения;
- `validation → done` требует успешной проверки без замечаний;
- `validation → revision` требует неуспешной проверки с замечаниями;
- `revision → validation` требует сохранённой доработки.

Примеры запрещённых действий:

```text
planning → validation
planning → done
execution → done
revision → done
validation_failed → done
done → execution
```

При отказе checkpoint не меняется, API не вызывается, а в append-only журнал записывается `transition_rejected` с причиной и запрошенной целью. Успешный модельный ход записывается отдельно как `stage_turn_completed`, а пользовательский переход — как `transition_applied` с `actor=user`.

Универсальный селектор `Запрос перехода` позволяет выбрать любую целевую фазу. Разрешённая цель проходит через те же guards, что и именованная кнопка этапа; запрещённая отклоняется с текущей фазой, разрешёнными целями и ожидаемым действием. Поэтому негативный сценарий проверяется обычным механизмом управления, а не специальной кнопкой-«атакой».

## Запуск

```bash
cd ~/Dev/AI_Advent_Challenge/day-15
uv sync --locked
cp .env.example .env
```

Добавить `DEEPSEEK_API_KEY` в `.env`, затем:

```bash
uv run --locked python main.py
```

Селектор рядом с кнопкой `Новая задача` показывает локальные checkpoint в формате `task-XX · цель · фаза #visit`. Выбор загружает активную фазу, весь маршрут `StageRun`, диалоги, артефакты и статус паузы. Цель сохранённой задачи заблокирована от случайного изменения; кнопка `Новая задача` сначала включает отдельный режим ввода цели, который можно подтвердить или отменить.

Основной экран показывает только действия текущей стадии. Над рабочей областью находится прокручиваемый маршрут всех запусков, например `✓ planning#1 → ✓ execution#1 → ✗ validation#1 → ● revision#1`; отдельным маркером отмечен просматриваемый запуск. Причина недоступности следующего перехода выводится рядом с кнопками.

Правая область разделена на вкладки:

- `Состояние` — checkpoint, ожидаемое действие, расход токенов текущего запуска и всей задачи;
- `Артефакт` — полный актуальный результат выбранного запуска;
- `Переходы` — постоянный журнал успешных и отклонённых переходов, пауз и LLM-ходов; здесь же находится технический селектор произвольной целевой фазы;
- `Prompt` — последний фактически отправленный набор сообщений.

Во время API-запроса отправленное сообщение сразу появляется в чате вместе с отметкой `Модель работает…`; индикатор и надпись `DeepSeek отвечает…` остаются видимыми, а конфликтующие действия блокируются. При ошибке незавершённый ход и её причина не исчезают. Подсказка поля сообщения зависит от текущей стадии. Отправить сообщение можно кнопкой, обычным `Enter` или `Ctrl+Enter`, выйти — `Ctrl+Q`.

Приложение не передаёт собственный `max_tokens`: окончательный предел задают модель и её контекстное окно. Для прикладных стадий используется `reasoning_effort=low`, чтобы внутреннее рассуждение не вытесняло полезный JSON и не расходовало токены без необходимости. Если API всё же вернул `finish_reason=length`, ход не изменяет артефакт, интерфейс прямо сообщает об обрезании, но фактический prompt, частичный сырой ответ, причина завершения и потраченные токены сохраняются в текущем `StageRun`. Вкладка `Prompt` показывает и запрос, и ответ модели; для успешного хода там находится полный сырой JSON до его разбора приложением.

Реальный изолированный execution-тест на синтетической пятишаговой технической задаче без `max_tokens` завершился с `finish_reason=stop`: 547 входных и 21 007 выходных токенов, артефакт — 25 751 символ. Тест подтвердил отсутствие прежнего обрыва на 4000, но также показал, почему интенсивность рассуждения важно ограничивать отдельно.

Чистый демонстрационный каталог:

```bash
uv run --locked python main.py --data-dir /tmp/day-15-demo
```

Локальные checkpoint и журналы хранятся раздельно и исключены из Git:

```text
data/tasks/task-XX.json
data/runs/task-XX.jsonl
```

## Результат демонстрации

В сохранённом реальном проходе проверена задача о безопасном релизе API с обязательными этапами, мониторингом, откатом, измеримыми критериями и рисками:

- запросы `planning → validation` и `planning → done` отклонены без изменения checkpoint;
- два planning-хода сформировали и уточнили план, после чего пользователь отдельно утвердил его;
- `execution #1` создал промежуточный артефакт с явными TODO в разделах отката и рисков;
- `validation #1` признала TODO блокирующими, пользователь отдельно отправил результат в `revision #1`;
- revision подготовила полный артефакт, а чистая `validation #2` получила актуальный результат без сообщений первой validation-сессии и завершилась без замечаний;
- пользователь отдельно принял проверку, итоговый маршрут завершился в `done`, а финальный артефакт совпал с принятой execution-версией и не содержит TODO/TBD.

Маршрут содержит пять независимых запусков: `planning #1 → execution #1 → validation #1 → revision #1 → validation #2 → done`. Пять успешных LLM-ходов использовали 14 319 входных и 16 398 выходных токенов, всего 30 717. Один planning-запрос завершился временной API-ошибкой без ответа и расхода токенов; повтор прошёл успешно, незавершённая пара не попала в историю.

## Выводы

- LLM определяет содержимое текущего артефакта, но не может изменить фазу задачи обычным ответом.
- Разделение модельного хода и пользовательского перехода позволяет обсуждать результат внутри стадии и не принимать его преждевременно.
- Новый `StageRun` на каждом повторном посещении ограничивает контекст: между стадиями передаются формализованные артефакты, а старые диалоги остаются только в аудите.
- Детерминированные guards запрещают перескоки и финал без успешной validation независимо от формулировок модели.

## Сценарий видео

1. Создать задачу, открыть вкладку `Переходы`, выбрать сначала `validation`, затем `done` — оба запроса будут отклонены, фаза останется `planning`, а причины появятся в журнале.
2. Написать в planning-сессию: «Составь план».
3. После ответа показать, что план появился, но активная фаза не изменилась.
4. Написать уточнение: «Добавь отдельный шаг проверки» — получить новую версию в той же planning-сессии.
5. Нажать `Утвердить план`: только тогда перейти в пустую execution-сессию, затем самостоятельно отправить `Выполни утверждённый план`.
6. Обсудить результат в execution несколькими сообщениями, затем отдельно нажать `Отправить на проверку`.
7. В созданной пустой validation-сессии самостоятельно отправить `Проверь результат`. Успешную проверку отдельно принять кнопкой `Завершить`; при замечаниях отправить результат на revision и отдельно попросить исправить замечания.
8. Открыть кнопками стадий и стрелками прошлые запуски, показать `validation #1` и чистую `validation #2`.
9. Вернуть execution к планированию и показать новый `planning #2`: в нём есть актуальный план как входной артефакт, но нет диалога `planning #1`.
10. До завершения поставить задачу на паузу, перезапустить приложение и продолжить активный запуск с сохранённого checkpoint.

## Проверки

```bash
uv run --locked python -m unittest -v
uv lock --check
```

Тесты проверяют несколько сообщений без автоматического перехода, обязательное пользовательское утверждение, новый `StageRun` при каждом посещении, чистую повторную validation без старого диалога, `planning #2` с сохранением прежнего запуска только для аудита, запрещённые перескоки, транзакционность отказов, паузу, восстановление, токены запусков и полный headless-маршрут до `done`. Прошли 17 тестов. При публикации повторные внешние LLM-вызовы и интерактивная визуальная проверка не выполнялись.
