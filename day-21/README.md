# День 21 — индексация документов

## Задание

Собрать локальный индекс документов с эмбеддингами и метаданными; сравнить
разбиение по фиксированному размеру и по структуре. Формат сдачи: видео и код.
Оригинальная формулировка находится в локальном `resources/task.md`.

## Корпус и решение

Корпус — 21 отслеживаемый Git файл `day-00/README.md` … `day-20/README.md`.
Индексатор читает только эти пути: локальные `resources/`, логи и `.env` в него
не попадают. В индексе сохраняются три стратегии для каждого файла:

| Стратегия | Правило |
| --- | --- |
| `fixed` | Окна до 112 токенов модели с перекрытием 16 токенов; могут пересечь заголовок Markdown |
| `structure` | Разделы по заголовкам Markdown, затем абзацы; длинные абзацы делятся до 112 токенов; разделы не смешиваются |
| `section_windows` | Разделы по заголовкам, внутри каждого — окна с перекрытием до 16 токенов; путь заголовков добавляется к тексту каждого чанка, пустые заголовки пропускаются |

`fixed` сохраняет контекст на стыке окон, но `section` описывает только начало
чанка: в конце может находиться другой раздел. `structure` удерживает границы
разделов и абзацев без перекрытия, поэтому иногда создаёт очень короткий чанк
из одного заголовка. `section_windows` совмещает границы разделов с перекрытием
внутри них; повтор заголовка помогает понять тему отдельного чанка, но занимает
часть лимита токенов и увеличивает индекс.

Все стратегии используют одну локальную модель
`sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` (ревизия
`e8f8c211226b894fcb81acc59f3b34ba3efd5f42`) и её токенизатор.
Предел в 112 токенов оставляет место для служебных токенов при максимальной
длине модели 128. Перед сохранением длина каждого чанка проверяется. Текст
чанка, нормализованный вектор, `chunk_id`, `strategy`, `source`, `title`,
`section` и число токенов хранятся в SQLite. Таблица `meta` содержит имя
модели, её ревизию, SHA256 корпуса и настройки разбиения. Новый индекс сначала полностью
создаётся во временном файле и лишь затем заменяет старый.

SQLite-файл и кэш модели создаются в `indexes/`, который исключён из Git.
Код и lock-файл позволяют пересоздать индекс из опубликованных README.
Для небольшого учебного корпуса поиск считает скалярное произведение
нормализованных векторов напрямую, без отдельного векторного сервера.

## Запуск

Нужен Python 3.12+ и `uv`. При первом запуске модель загружается с Hugging
Face в локальный кэш; платный API не используется.

```bash
cd day-21
export HF_HOME="$PWD/indexes/hf-cache"
uv sync --locked
uv run --locked python indexer.py demo
```

`demo` заново строит индекс и показывает таблицы с правилами трёх стратегий,
их компромиссами, числом и длиной чанков, примером с полями `source`, `title`,
`section`, `chunk_id`, затем метрики и ранги по пяти одинаковым запросам.
Итоговый блок объясняет результат и ограничение оценки. Цвета видны в
интерактивном терминале; таблицы остаются читаемыми без цвета. Для записи
рекомендуется ширина терминала от 110 столбцов. Команды `build`, `search` и
`compare` сохраняют JSON-вывод для дальнейшей обработки:

```bash
uv run --locked python indexer.py build
uv run --locked python indexer.py search "Как работает память агента?" --strategy structure
uv run --locked python indexer.py search "Как работает память агента?" --strategy fixed
uv run --locked python indexer.py search "Как работает память агента?" --strategy section_windows
uv run --locked python indexer.py compare
```

Команда `compare` выполняет пять одинаковых поисковых запросов для трёх
стратегий. Для каждого запроса задан ожидаемый README; сравниваются ранг первого
чанка этого файла среди первых пяти результатов, доля попаданий `hit@5`, средний обратный
ранг `MRR@5`, количество чанков и длина чанка в токенах. Это небольшой
контрольный набор, а не общая оценка качества поиска.

## Результат локального прогона

28.09.2026 индекс построен по 21 README: 16 403 слова, SHA256 корпуса
`87623fcecd8eb2e83c05d99ed489cd87517c45645cec31f091a372394b24707d`.

| Стратегия | Чанков | Средняя длина, токены | Максимум | hit@5 | MRR@5 |
| --- | ---: | ---: | ---: | ---: | ---: |
| `fixed` | 381 | 109,4 | 112 | 5/5 | 0,84 |
| `structure` | 505 | 71,0 | 112 | 5/5 | 0,767 |
| `section_windows` | 503 | 97,8 | 110 | 5/5 | 0,9 |

Для первых четырёх запросов фиксированная стратегия поставила нужный README
на первое место; для пятого — на пятое. Структурная поставила нужный README
на первое место для трёх запросов, на второе — для одного и на третье — для
одного. `section_windows` поставила нужный README первой по четырём запросам
и второй по одному. На этом контрольном наборе она получила наибольший MRR@5,
сохраняя границы разделов. Но для запроса об индексе Datex нужный файл оказался
первым, а чанк с точным описанием индекса — вторым: метрика по файлу не измеряет
полноту найденного ответа. Пять запросов не позволяют обобщать разницу на
другие корпуса и задачи.

## Проверки

```bash
uv run --locked python -m unittest -v
uv run --locked python -m compileall -q indexer.py test_indexer.py
uv lock --check
git diff --check
```

Тесты разбиения и SQLite используют подменную модель без сетевых запросов.
28.09.2026 прошли семь тестов, компиляция, `uv lock --check` и
`git diff --check`. Реальный локальный прогон построил индекс и выполнил
`demo`, `compare` и `search` на модели с зафиксированной ревизией. Визуальная
проверка терминального вывода выполнена при ширине 110 столбцов.
