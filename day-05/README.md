# День 5. Версии моделей

Один и тот же запрос выполняется на слабой, средней и сильной модели. Для каждого ответа измеряются время, токены и стоимость; затем сравниваются качество, скорость и косвенная ресурсоёмкость. Формат сдачи: видео, код, короткий вывод и ссылки.

## Решение

Терминальное приложение на Textual сравнивает три модели:

| Роль в эксперименте | Модель | Провайдер |
|---|---|---|
| Условно слабая | [NVIDIA Nemotron 3.5 Lightning](https://openrouter.ai/nvidia/nemotron-3.5-lightning:free) | OpenRouter Free |
| Условно средняя | [DeepSeek V4 Flash](https://api-docs.deepseek.com/quick_start/pricing/) | DeepSeek |
| Условно сильная | [DeepSeek V4 Pro](https://api-docs.deepseek.com/quick_start/pricing/) | DeepSeek |

Роли заданы до эксперимента и не являются его выводом. Меньший размер или более низкая цена сами по себе не означают худшее качество.

В приложении два независимых эксперимента:

1. `prompt.txt` — выбор оптимального набора задач релиза.
2. `prompt-02.txt` — точный вывод и исправление Python-кода с замыканиями.

Каждый промпт без изменений отправляется всем трём моделям. Два промпта расширяют минимальное требование задания и позволяют не делать вывод по единственному примеру.

Одна кнопка выполняет ровно **6 последовательных API-вызовов**: Nemotron → Flash → Pro для первой задачи, затем в том же порядке для второй. Дополнительного запроса к анализатору нет. Итоговую оценку выполняют пользователь и Codex по сохранённым ответам.

## Подготовка

Требуются Python 3.11 или новее и `uv`.

```bash
cd ~/Dev/AI_Advent_Challenge/day-05
uv sync --locked
```

Создай локальный `.env` из `.env.example` и заполни:

- `DEEPSEEK_API_KEY`;
- `OPENROUTER_API_KEY`;
- `DEEPSEEK_MODEL_MEDIUM`;
- `DEEPSEEK_MODEL_STRONG`;
- `OPENROUTER_MODEL_WEAK`.

Настройки новых запросов: `temperature=0`, `top_p=1`, `max_tokens=4096`, без streaming. Thinking отключён у DeepSeek, reasoning — у OpenRouter. OpenRouter принимает только конкретную модель с суффиксом `:free`; маршрутизация запрещает платную подмену.

## Запуск и запись видео

```bash
uv run python main.py
```

1. Начни запись экрана.
2. Проверь оба промпта и нажми **«Запустить сравнение»**.
3. Дождись шести ответов и локальной проверки.
4. Покажи вкладки **«Задача 1 · ответы»**, **«Задача 2 · ответы»**, **«Проверки»** и **«Метрики»**.
5. Сохрани новую запись как `resources/day-05-result-2prompts.mp4`.

После шестого ответа автоматически открывается сравнение первой задачи. Для каждой модели показаны статус, время, входные и выходные токены, стоимость, локальная проверка и первые 900 символов ответа. Полный текст находится в соседней вкладке модели.

Кнопка **«Последний результат»** открывает сохранённую запись без API. Конкретную сессию можно открыть так:

```bash
uv run python main.py --session resources/results/ИМЯ_СЕССИИ.json
```

## Что измеряется

- **Время** — длительность одного HTTP-вызова от отправки до получения полного ответа. Ожидание своей очереди не учитывается.
- **Токены** — входные, выходные и общие значения из `usage` API.
- **Стоимость USD ≈** — локальная оценка по тарифам на дату запуска, а не подтверждённое списание. Для OpenRouter `:free` показывается `$0 Free`.
- **Ресурсоёмкость** — токены и стоимость как доступные косвенные показатели. GPU, RAM и энергия серверов через используемые API не измеряются.
- **Качество** — локально проверенные факты плюс ручная оценка правильности объяснения, полноты и соблюдения условий. Скорость, длина и цена не повышают оценку качества.

Запросы идут последовательно, поэтому сетевые условия в разные моменты могут отличаться. Один прогон не доказывает общий рейтинг моделей.

## Независимые проверки

Проверки работают только для неизменённых штатных промптов. SHA-256 не позволяет применить старый эталон к отредактированной задаче.

Для задачи релиза приложение самостоятельно перебирает все 64 подмножества и проверяет:

1. оптимальный набор при бюджете 15;
2. второй допустимый набор при бюджете 15;
3. оптимальный набор при бюджете 12.

Для машинного чтения модели возвращают в разделе `Итог` один JSON-блок с наборами и показателями. Перебор подтверждает итоговые факты, но не качество доказательства оптимальности.

Для задачи Python проверяются:

1. точный исходный stdout;
2. сигнатура и контракт исправленной `build` на контрольных случаях;
3. точный stdout после исправления;
4. все `assert`, предложенные моделью.

Код модели выполняется в отдельном процессе с AST allowlist, минимальными builtins, пустым окружением, временным каталогом и ограничениями CPU, памяти и времени. Неподдерживаемый или неоднозначный ответ получает «Не проверено», без автоматического ранжирования.

### Ручная оценка

- **Flash** единственный правильно назвал все три требуемых набора задачи релиза. В Python-задаче он предложил правильное исправление и восемь работающих assert, но неверно указал исходный stdout. Ответ на задачу релиза содержит около 750 слов без JSON и нарушает лимит 350 слов.
- **Pro** правильно нашёл основной оптимум релиза, но ошибся со вторым набором и оптимумом при бюджете 12. Объяснение ошибок Python и исправленный код корректны, однако оба заявленных stdout неверны и противоречат коду и проверкам самого ответа.
- **Nemotron** также правильно нашёл только основной оптимум релиза. В остальных результатах нарушены зависимости задач. Исправленная функция Python проходит контрольные случаи, но объяснение исходного поведения противоречиво, а четыре из семи предложенных assert неверны.

### Короткий вывод

В этом прогоне победил **DeepSeek V4 Flash**: он показал лучший формализованный результат, оказался самым быстрым и дал наиболее полный ответ. Его недостатки — один неверный stdout, нарушение лимита слов и наибольшее число токенов. **DeepSeek V4 Pro** занял второе место по ручной оценке: его объяснение Python лучше Nemotron, но итоговые факты часто ошибочны, а выполнение оказалось самым долгим и дорогим. **Nemotron** занял третье место; его преимущество — нулевая стоимость API.

Это результат одного последовательного прогона, а не общий рейтинг моделей. Скорость зависит от нагрузки провайдеров, а автоматические баллы проверяют только семь формализованных пунктов.

## Ошибки и сохранение

Сессия создаётся в `resources/results/<UTC-время>-<id>.json` до первого запроса и атомарно обновляется после каждого ответа. Сохраняются промпты, полные ответы, статусы, метрики, тарифная база и локальные проверки. Ключи и заголовки авторизации не сохраняются.

После ошибки остальные модели продолжают работу. `finish_reason`, отличный от `stop`, означает неполный ответ. Автоматических повторов нет. При HTTP 429 сохраняются только безопасные числовые сведения о квоте и `retry-after`, если они доступны.

## Проверки проекта

```bash
uv run python -m unittest -v
```

Тесты используют `httpx.MockTransport` и не вызывают реальные API. Они проверяют:

- ровно шесть последовательных запросов и отсутствие седьмого;
- одинаковые сообщения и параметры внутри каждой задачи;
- сбор времени, токенов и стоимости;
- ошибки, неполные ответы, сохранение и отсутствие секретов;
- карточки сравнения и просмотр сессии без сети;
- оба локальных проверяющих модуля и их безопасные границы.

Unit-тесты подтверждают локальную логику, но не доступность API и внешний вид в настоящем терминале. Сессия из раздела «Результат прогона» подтверждает только фактические ответы и метрики конкретного запуска; визуальная проверка видео проводится отдельно.
