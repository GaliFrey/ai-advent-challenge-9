# Интерфейс и сценарий дня 5

## Сценарий

Одна кнопка запускает два промпта на трёх моделях последовательно: ровно шесть запросов, включая ошибки. Порядок: Nemotron → Flash → Pro для первой задачи, затем тот же порядок для второй. После шестой попытки выполняются локальные проверки; ответы оценивают пользователь и Codex. Дополнительного запроса к анализатору нет.

## Экран

- Верхняя строка: название и номер дня.
- Два редактируемых промпта во вкладках; при запуске редакторы сворачиваются, их можно снова раскрыть.
- Кнопки запуска, просмотра последней записи и раскрытия промптов.
- Статус текущего этапа: ответы → локальная проверка → завершено.
- Таблица шести ответов (задача × модель): статус, секунды, входные/выходные токены, стоимость USD ≈.
- У ожидающих запросов статус «В очереди», таймер идёт только у текущего запроса; ожидание очереди не включается в метрики.
- В каждой задаче первая вкладка показывает три вертикальные карточки: модель, статус, время, токены, стоимость, результат локальной проверки и первые 900 символов ответа. Полный текст доступен в соседней вкладке модели.
- Отдельные вкладки показывают независимые проверки и сводные метрики.
- Идентификатор сохранённой сессии и подсказки клавиш.

Оформление: тёмный фон, приглушённые границы, один голубой акцент; зелёный для завершения, янтарный для неполного ответа, красный для ошибки. Интерфейс остаётся отзывчивым во время сетевых операций. При нехватке места доступны прокрутка и сворачивание редакторов.

## Поведение

- Запуск и открытие сохранённой сессии блокируются на время обработки.
- Все участники имеют одинаковый лимит ответа 4096 токенов; лимит показан в интерфейсе. Превышение OTPM размером ожидаемого ответа объясняется отдельно от ожидания сброса квоты.
- Третий участник — Nemotron 3.5 Lightning через OpenRouter; чтение OPENROUTER_API_KEY, конкретная модель :free, максимальная цена $0 и отключённое reasoning. Дополнительной паузы перед запросами нет.
- Нет автоповторов после ошибок и обрезания ответа. HTTP 429 объясняется как лимит API; сохраняются только числовые заголовки квоты и retry-after, время ожидания видно в ошибке.
- Доступные результаты сохраняются сразу; сбой одного API не отменяет остальных.
- Приложение не отправляет ответы на дополнительный анализ и не назначает общего победителя. Ручная оценка проводится по сохранённому JSON и полным текстам.
- Для задачи релиза локальный модуль перебирает все 64 набора и проверяет оптимум и второй результат при бюджете 15, а также оптимум при бюджете 12. Итог — число совпавших результатов из трёх.
- Для задачи Python проверяются исходный stdout, контракт `build`, новый stdout и assert модели. Итог — число пройденных пунктов из четырёх. Неизвестный результат исключает числовое ранжирование задачи; ничья допустима.
- Обе проверки привязаны к SHA-256 точного текста промпта. Изменённый текст показывается как непроверенный. При открытии сохранённой сессии проверки пересчитываются в памяти.
- Просмотр сохранённой сессии полностью локальный. Формат v2 хранит результаты по задаче и модели и сводку; старый v1 преобразуется только в памяти. Неизвестные метрики не заменяются нулём и дают неизвестную сумму.

## Реализация

`main.py` и `app.tcss` отвечают за Textual-интерфейс и карточки сравнения. `experiment.py` содержит конфигурацию, HTTP-запросы через httpx, последовательное асинхронное выполнение, тарифы и сохранение JSON. `prompt.txt` — задача релиза, `prompt-02.txt` — разбор Python-кода. Общих импортов из предыдущих дней нет.

`verification.py` сопоставляет обе штатные задачи с эталонами, перебирает планы релиза, разбирает разделы ответов, собирает проверки и формирует вывод. `verification_worker.py` проверяет ограниченное AST-подмножество Python в отдельном процессе без окружения приложения с ограничениями ресурсов. Новый прогон выполняет проверку в отдельном потоке после шести ответов; UI остаётся отзывчивым. При локальном открытии проверка синхронная, не более двух секунд на Python-ответ. Неподдерживаемая конструкция не объявляется ошибкой решения.

Сначала создаётся файл сессии. Шесть вызовов выполняются в цикле с `await`, без перекрытия; до отправки сохраняется `active_request`, после ответа вызывается сохранение через временный файл и атомарную замену. Седьмого вызова нет. Textual worker выполняет этот сценарий без блокировки UI; отдельный таймер обновляет индикаторы ожидания.
