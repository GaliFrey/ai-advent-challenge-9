# День 22 — первый RAG-запрос

## Задание

Реализовать цепочку «вопрос → поиск релевантных чанков → контекст и вопрос →
LLM», сравнить ответы с RAG и без него. Подготовить 10 контрольных вопросов
с ожидаемыми фактами и источниками. Сдача: видео и код.
Оригинальная формулировка хранится локально в `resources/task.md`.

## Решение

Отдельный CLI использует индекс дня 21: README дней 0–20, SQLite,
`section_windows`, пять лучших чанков по скалярному произведению
нормализованных эмбеддингов. `retrieval.py` подключает существующий
`day-21/indexer.py` без копирования и изменения его кода. Поэтому для запуска
нужен весь репозиторий, включая день 21.

| Режим | Что получает LLM |
| --- | --- |
| `plain` | Общая инструкция и вопрос; индекс и модель эмбеддингов не загружаются |
| `rag` | Та же инструкция, тот же вопрос, тексты пяти найденных чанков с источниками |
| `compare` | Два независимых вызова — сначала `plain`, затем `rag` |

В обоих режимах используется один system prompt, `temperature=0` и
отключённое thinking. Приложение не задаёт `max_tokens` и не просит отвечать
кратко; остаются ограничения самой модели и API. История и ответы другого
режима не передаются. По умолчанию модель — `deepseek-flash`, её можно изменить
через `DEEPSEEK_MODEL`. Температура 0 не гарантирует побитовую повторяемость.

LLM получает локальные ссылки `[S1]` … `[S5]`, `source`, `title`, `section`,
`chunk_id` и текст. Инструкция требует опираться на источники, считать их
данными, а при нехватке информации прямо обозначать пробелы. Проверка
номеров ссылок автоматическая; проверка того, подтверждает ли фрагмент
утверждение, выполняется вручную. Даже при пустой выдаче модель получает
пустой список источников; приложение не заявляет, что в базе точно нет ответа.

Перед поиском проверяются модель и ревизия эмбеддингов, SHA256 текущего
корпуса и наличие стратегии. Устаревший индекс вызывает ошибку с просьбой
пересобрать его. SQLite открывается только для чтения. Используются модель
и кэш дня 21; векторный сервер, реранкинг и дополнительный LLM-судья не нужны.

## Запуск

Нужны Python 3.12+, `uv`, индекс дня 21 и ключ DeepSeek.

```bash
cd day-22
uv sync --locked
cp .env.example .env
# Заполнить DEEPSEEK_API_KEY в локальном .env.
uv run --locked python main.py ask "Как в дне 20 проверяется скачанный отчёт?"
uv run --locked python main.py ask "Какая память реализована в дне 11?" --mode plain
uv run --locked python main.py ask "Какая память реализована в дне 11?" --mode rag
```

Если локальный `.env` уже настроен, повторно копировать шаблон не нужно.
Системные переменные имеют приоритет. Ключ не сохраняется в результатах.
Внешнему DeepSeek передаются вопрос и, для режима RAG, фрагменты README.

Если индекс отсутствует или устарел:

```bash
cd ../day-21
uv sync --locked
HF_HOME="$PWD/indexes/hf-cache" uv run --locked python indexer.py build
cd ../day-22
```

При первом построении загружается модель эмбеддингов; последующие прогоны
с заполненным кэшем могут использовать `HF_HUB_OFFLINE=1`.

## Контрольный набор и оценка

В `questions.json` заранее записаны 10 вопросов, ожидаемые факты и пути
источников: шесть вопросов о конкретных решениях, два о нескольких
документах и два без ответа в корпусе (p95 нагрузочного теста Datex;
бюджет и SLA трёх ВМ). Ожидания не передаются в LLM.

```bash
uv run --locked python main.py benchmark
```

Это 20 платных LLM-вызовов, без автоматических повторов. При ошибке прогон
останавливается, уже полученные ответы сохраняются. Новый запуск создаёт
новый файл и выполняет все вызовы заново. Ошибка API или обрыв по лимиту
не считаются полноценным ответом.

Каждый прогон создаёт `resources/<команда>-<UTC timestamp>.json`.
После каждого успешного ответа файл атомарно обновляется. В нём хранятся
вопросы и ожидания, параметры, метаданные индекса, точные messages,
найденные фрагменты, ответы, `usage`, время поиска и LLM, проверка ссылок
и ручные оценки. Время загрузки модели не входит во время поиска.
Файлы результатов остаются локальными и исключены из Git.

Шкала качества:

- **2** — все ожидаемые факты переданы верно, неподтверждённых утверждений нет;
  для вопроса без ответа — корректное признание нехватки данных.
- **1** — полезный, но неполный ответ либо ответ с отдельной ошибкой.
- **0** — нужных фактов нет или основной ответ неверен. Честное «не знаю»
  на разрешимый вопрос получает 0 за полноту, но не помечается как выдумка.

Отдельные поля оценки: неподтверждённые утверждения (`unsupported`),
обоснованность ссылок (`citations`), полнота найденных сведений (`retrieval`),
корректность отказа (`abstention`) и текстовое объяснение (`note`).
`na` означает, что критерий неприменим. Отказ при неполной выдаче может
быть обоснованным, даже если ожидаемые факты есть в полном корпусе.

Просмотр сохранённых результатов и оценка не используют сеть, ключ или
модель эмбеддингов. Вместо `<timestamp>` нужно подставить имя своего файла:

```bash
uv run --locked python main.py show 'resources/benchmark-<timestamp>.json' --question q05 --chunks
uv run --locked python main.py review 'resources/benchmark-<timestamp>.json' \
  --question q05 --mode rag --quality 2 --unsupported no \
  --citations pass --retrieval full --abstention na \
  --note "Все ожидаемые факты подтверждены переданными фрагментами."
uv run --locked python main.py show 'resources/benchmark-<timestamp>.json' --summary-only
```

Пример команды оценки иллюстрирует формат, а не заранее заданный результат.
До оценки таблица показывает `—`, а не автоматически выдуманный балл.
Доля найденных ожидаемых файлов считается отдельно: наличие README
в top-5 не доказывает, что в выдаче присутствует нужный фрагмент.

## Результат прогона 29.09.2026

Сохранённый локальный файл:
`resources/benchmark-20260929T160614.596476Z.json`. Все 20 вызовов
`deepseek-flash` завершились с `finish_reason=stop`. Использован прежний
корпус из 21 README с SHA256
`87623fcecd8eb2e83c05d99ed489cd87517c45645cec31f091a372394b24707d`.
Этот сохранённый прогон выполнялся с `max_tokens=800`; после него явный
лимит генерации был убран из новых запросов. Поэтому приведённые ниже
баллы относятся именно к сохранённому прогону, а не к новой настройке.
Ожидания зафиксированы до вызовов. После прогона Codex сопоставил каждый
ответ с ожиданиями и сохранёнными фрагментами; это содержательная оценка
ассистента, а не независимая оценка человеком или автоматический тест.

| --- | ---: | ---: | --- |

| q02 — интервал summary и ошибка | 0 | 2 | Полный ответ |

| q08 — MCP дней 19 и 20 | 0 | 0 | День 20 не найден, от дня 19 попало только задание |

| **Всего** | **4/20** | **12/20** | |

Без RAG модель не ответила на восемь вопросов о конкретных решениях проекта.
С RAG полностью отвечены три из этих восьми вопросов, ещё два — частично.
На два вопроса без ответа в корпусе оба режима корректно сообщили о нехватке
данных. Вымышленных фактов и несуществующих номеров ссылок не обнаружено.
Модель иногда говорит «в переданных источниках» даже в режиме без RAG,
где источники вообще не передавались; это неточная формулировка отказа.

Для семи из восьми разрешимых вопросов поиск нашёл все ожидаемые файлы,
но полный набор необходимых сведений присутствовал только для трёх.
Это подтверждает ограничение оценки поиска по имени README из дня 21:
релевантный файл и фрагмент, содержащий ответ, — разные результаты.
Поиск и генерация работают сквозным образом, но качества простого top-5
недостаточно для части составных и точных вопросов. В этом эксперименте
не подбирались вопросы или параметры под удачные ответы.

Суммарный расход: **2169 токенов без RAG**, **13 274 с RAG**, всего **15 443**.
Сумма времени LLM-вызовов: 10,275 с и 13,048 с соответственно, без загрузки
эмбеддингов и поиска. Это один небольшой прогон; баллы не являются общей
метрикой качества модели. Строгая общая инструкция способствует честным
отказам, поэтому эксперимент демонстрирует прирост доступных фактов,
а не снижение наблюдавшихся галлюцинаций.

Первичная попытка из сетевой песочницы завершилась сетевой ошибкой до
получения ответа. Полный прогон выполнен после явного разрешения пользователя
передавать вопросы и фрагменты README в DeepSeek; повторных успешных
сравнительных прогонов не было.

В записи показаны живые сравнения q04, q08 и q06: ответы без RAG и с RAG,

Основной способ показать работу — живое TUI на одном экране:

```bash
cd day-22
uv run --locked python main.py tui
```

Сверху выбирается один из десяти вопросов. **«Спросить · 2 запроса»**
отправляет этот вопрос сначала без RAG, затем с RAG. По мере завершения
запросов ответы появляются рядом. Ниже видны пять найденных чанков, их
источники и сходство. Список S1…S5 открывает полный текст выбранного чанка.
Отдельно показаны токены, время LLM и поиска, а также число ожидаемых
файлов, найденных среди источников. Числовой балл качества в TUI не выводится:
он требует ручной оценки, которую текущий запрос ещё не проходил.

**«Демо · 20 запросов»** последовательно отправляет все десять вопросов
в обоих режимах. Строка состояния показывает текущий вопрос, режим и число
готовых вызовов. После завершения можно свободно выбирать любой вопрос и
смотреть оба ответа и переданный контекст. Новое демо создаёт отдельный
результат в `resources/benchmark-<UTC timestamp>.json`; запуск одного
вопроса создаёт `resources/ask-<UTC timestamp>.json`. Файл обновляется после
каждого успешного ответа; при ошибке сохранённая часть остаётся доступной.
Повторный запуск заново выполняет запросы и расходует API-лимит. Демо не
запускается автоматически при открытии TUI.

Для записи: запустить TUI → выбрать q01 и показать два ответа → раскрыть
S4/S5 в списке чанков → нажать **«Демо · 20 запросов»** → показать, как
появляются ответы на следующих вопросах → после завершения выбрать q05
(пример неполной выдачи) и q09 (корректное признание отсутствия данных).
Если нужно избежать повторной оплаты при подготовке кадра, ранее сохранённый
JSON можно открыть аргументом:

```bash
uv run --locked python main.py tui resources/benchmark-20260929T160614.596476Z.json
```

В таком случае ответы и чанки сразу доступны для просмотра, а кнопки
«Спросить» и «Демо» начинают **новый** прогон. Для выхода — **Ctrl+Q**.
При первом живом запуске эмбеддинг-модель загружается из кэша дня 21;
это может занять несколько секунд до первого LLM-запроса. Рекомендуется
терминал от 120 столбцов × 45 строк. При меньшей высоте содержимое
прокручивается.

### Журнал и ошибки

Каждый запуск TUI создаёт файл `resources/logs/tui-<UTC timestamp>-<id>.jsonl`.
В нём записываются начало сеанса, проверка индекса, загрузка модели,
запуск и завершение каждого вызова, число токенов и чанков. При ошибке
записываются этап, тип и код ошибки, а также имена файлов и номера строк
стека. API-ключ, вопросы, полный контекст и ответы в этот журнал не пишутся.
В JSON-результате при ошибке есть поле `error` с этапом и кодом; результаты
успешных вызовов сохраняются. В строке состояния показано имя журнала.
Все эти файлы остаются локальными в игнорируемом `resources/`.

Для просмотра последних событий после выхода из TUI:

```bash
tail -n 20 "$(ls -t resources/logs/*.jsonl | head -n 1)"
```

Старый неудачный файл `resources/ask-20260929T164705.688647Z.json` был
создан до появления журнала и поля `error`; точную причину именно того
запуска восстановить нельзя. Локальное воспроизведение выявило два сбоя
загрузки модели: сетевые проверки Hugging Face даже при наличии кэша и
запуск служебного процесса Python после открытия TUI. При наличии полного
снимка модели приложение теперь использует кэш без сетевых запросов;
служебный процесс инициализируется до открытия экрана.

Пошаговый CLI-показ прежнего сохранённого прогона остаётся доступен командой
`uv run --locked python main.py demo`. Он не вызывает LLM.
Видео сохраняется локально как `resources/day-22-result.mp4`.
