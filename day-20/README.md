# День 20 — оркестрация трёх MCP-серверов

## Задание

Зарегистрировать несколько MCP-серверов. Агент должен выбрать инструменты,
маршрутизировать вызовы и выполнить длинный сценарий с инструментами разных
серверов. Сдача: видео и код. Оригинал: `resources/task.md`.

## Решение

Один запрос «Проанализируй SSH-входы за последние сутки и сохрани отчёт на моём
компьютере» проходит через три отдельные учебные ВМ:

| ВМ и MCP-сервер | Инструмент | Результат |
| --- | --- | --- |
| `ai-advent-20-mcp-source` | `read_ssh_logins` | Ограниченный снимок реальных `Accepted`-входов из `ssh.service` journald |
| `ai-advent-20-mcp-analyze` | `analyze_logins` | Количество входов, уникальные IP, группировки по пользователям и IP |
| `ai-advent-20-mcp-report` | `save_report` | Markdown-файл на ВМ, размер и SHA256 |

Клиент затем скачивает файл с ВМ отчётов в `day-20/reports/`, сравнивает размер
и SHA256 и показывает отдельный шаг **«Отчёт получен»** с локальным путём.
Только после этого итог считается успешным. Отчёты и полные JSONL-трассы
остаются локальными и исключены из Git.

Агенту доступны три именных псевдонима инструментов:
`source__read_ssh_logins`, `analyze__analyze_logins`, `report__save_report`.
Ответ первого шага даёт `source_ref`, второго — `analysis_ref`. Агент выбирает
инструмент и передаёт полученный идентификатор. Клиент сверяет его и передаёт
на следующую ВМ точные структурированные данные предыдущего MCP-ответа.
Каждый сервер проверяет SHA256 полученных данных. Порядок и ID проверяются
клиентом; неверный маршрут или подменённый ID останавливают сценарий.
Вызовы зависимы и выполняются по одному.

Модель получает количество входов, период, хеши и агрегаты. Полные события
с IP и именами пользователей в её запрос не включаются. После третьего вызова
клиент формирует итог из проверенных данных без дополнительного ответа LLM:
реальный прогон выявил, что модель могла неверно назвать ВМ отчётов исходной ВМ.
Текст SSH-журнала считается данными. Источник читает доступную историю journald
на момент вызова без фонового сборщика. `Accepted` подтверждает успешную
аутентификацию, но не действия внутри сеанса; доступная история может быть
короче запрошенного периода. Лимит — 1000 входов за 1–168 часов; вместо
усечённого отчёта при превышении возвращается ошибка.

## Подготовка

Нужны три указанных SSH-алиаса в `~/.ssh/config`, SSH-агент и Python 3.12 на ВМ.
На ВМ размещены `uv`, `pyproject.toml`, `uv.lock` и соответствующий
`*_server.py` в `/home/heimdall/ai-advent-day20`. Зависимости установлены
командой `uv sync --locked --python /usr/bin/python3.12`. Сервера запускаются
клиентом через SSH/STDIO по требованию; отдельных сетевых портов и постоянных
служб нет. Пользователь на ВМ-источнике состоит в `systemd-journal`, чтобы
читать записи `ssh.service` без root.

Локально:

```bash
cd day-20
uv sync --locked
cp .env.example .env
# Заполнить DEEPSEEK_API_KEY только локально.
uv run --locked python main.py
```

TUI показывает статус трёх серверов, короткие решения LLM и результаты
каждого вызова. Выбор шага раскрывает маршрут, аргументы и краткий результат.
Полные запросы LLM и MCP сохраняются в `sessions/*.jsonl`; журнал содержит
SSH-события, IP и имена пользователей и не должен публиковаться без проверки.
Ключ API не записывается. В демонстрации видны три выбора сервера, затем
«Отчёт получен» и локальный путь.

## Проверки

```bash
uv run --locked python -m unittest -v
uv run --locked python -m compileall -q . -x '/\.venv/'
uv lock --check
uv run --locked python check_pipeline.py  # прямые MCP-вызовы без LLM
uv run --locked python check_agent.py     # решения LLM подменены локально
```

`check_agent.py --llm` выполняет реальный запрос DeepSeek. Для него нужен
локальный ключ и явное разрешение на передачу провайдеру метаданных SSH-журнала
(числа входов, периода и хешей). IP и имена пользователей туда не отправляются.

25.09.2026 прошли четыре локальных unit/headless-теста, компиляция и проверка
`uv.lock`. Прямой сквозной прогон на трёх ВМ обработал 15 входов, создал и
скачал отчёт с совпадающим SHA256. Прогон полного агентского цикла с
подменёнными решениями LLM обработал 16 входов, три инструмента на трёх ВМ и
скачал отчёт размером 813 байт с проверенным SHA256. После явного разрешения
пользователя один реальный прогон DeepSeek выбрал верный порядок трёх серверов,
обработал 17 входов и завершился локальным отчётом размером 813 байт с
совпавшим SHA256. В финальном тексте модель неверно обозначила ВМ отчётов;
после этого итоговый текст переведён на формирование клиентом. Повторный
внешний вызов не выполнялся. В прежнем четвёртом запросе LLM оказался путь
`/home/heimdall/...` с именем локального пользователя, совпадающим с именем
пользователя в SSH-событиях; сами записи и IP не передавались. В обновлённом
коде четвёртого запроса нет: проверка новой JSONL-трассы с подменённой LLM
подтвердила три раунда и отсутствие IP, имени пользователя и пути к отчёту в
модельных запросах. Этот вывод относится к проверенной трассе, а не к новому
внешнему прогону.

На видео записаны два последовательных запроса в одном сеансе TUI. В каждом
DeepSeek выбрал `SOURCE → ANALYZE → REPORT`, после чего клиент скачал отчёт.

запросов LLM, шесть MCP-вызовов и два события «Отчёт получен» без ошибок.
Трасса и отчёты остаются локальными и не включены в Git.

В обоих прогонах `source_ref` и `analysis_ref` совпали между зависимыми
