# День 13. Состояние задачи

Агент выполняет задачу через формализованный конечный автомат:

```text
planning → execution (три шага) → validation ─ passed ─────────────────→ done
                                      └ failed → revision → validation
                                                   ↑          ├ passed → done
                                                   └ failed ──┘ (не более двух revision)
                                                              └ второй failed → done_with_issues
```

Состояние задачи хранится отдельно от текста prompts и содержит этап, текущий шаг, ожидаемое действие, результаты завершённых шагов и последний фактически отправленный запрос. Задачу можно поставить на паузу после любого атомарного API-turn, закрыть приложение и продолжить с сохранённого checkpoint без повторного объяснения цели.

## Workflow-профили

Для этого агента созданы два новых профиля процесса:

- `Инженерный результат` — технический планировщик, исполнитель, независимый проверяющий и инженер по доработке;
- `Объясняющий материал` — редактор структуры, автор, выпускающий редактор и выпускающий автор доработки.

Профиль определяет роли и инструкции стадий, но не изменяет состояние напрямую. Переходы разрешает только код конечного автомата. После начала задачи профиль фиксируется, чтобы возобновление не изменило процесс задним числом.

## Модели стадий

Стадии намеренно используют разные модели и два API-провайдера:

| Стадия | Модель | API |
| --- | --- | --- |
| `planning`, `execution` | `deepseek-v4-flash` | DeepSeek |
| `validation` | `openai/gpt-5.6-sol` | OpenRouter |
| `revision` | `deepseek-v4-pro` | DeepSeek |

Модель validation закреплена точным ID для воспроизводимости. Независимый валидатор не получает право менять состояние: он возвращает структурированные нарушения и улучшения, а решение `passed` вычисляет приложение — пустой список `issues` означает успех. Каждое нарушение обязано содержать критерий, доказательство из результата, описание проблемы и требуемое исправление. Список неблокирующих `improvements` должен содержать минимум один полезный пункт даже при успешной проверке.

## Состояние и переходы

У задачи независимо хранятся `phase` и `status`. Пауза не является отдельным этапом и поэтому не размножает состояния вроде `paused_execution`.

| Этап | Текущий шаг | Ожидаемое действие |
| --- | --- | --- |
| `planning` | формирование плана | составить план |
| `execution` | один из трёх сохранённых шагов | выполнить этот шаг |
| `validation` | проверка полного результата | проверить и собрать итог |
| `revision` | доработка совокупного результата | исправить по замечаниям |
| `done` | завершено | действий нет |

Статус может быть `ready`, `paused`, `failed`, `done` или `done_with_issues`. Ошибка API либо неверный формат ответа не продвигают checkpoint: интерфейс предлагает повторить ту же стадию.

Validation возвращает замечания по строгой схеме. При их наличии она сохраняет инструкцию и лучшую текущую версию, после чего запускается revision-turn и повторная validation. Допускается не более двух доработок: проверка без нарушений завершает задачу раньше, а замечания после второй доработки фиксируют `done_with_issues`. Поэтому автомат не может зациклиться и всегда приходит в `done`.

Во время выполняющегося запроса кнопка паузы устанавливает флаг. Текущий API-turn завершается и сохраняется атомарно, а следующий уже не начинается. Это исключает неоднозначность, был ли частично отменённый шаг выполнен.

## Сборка запросов

Каждая стадия получает новый компактный запрос:

```text
базовые правила автомата
+ инструкции стадии из workflow-профиля
+ исходная цель
+ сохранённый план
+ результаты только завершённых шагов
```

Planning возвращает JSON из трёх шагов. Execution выполняет ровно один текущий шаг за вызов. Validation проверяет все результаты и формирует итог для пользователя. При необходимости revision получает замечания и возвращает целиком исправленную версию. Сама модель не выбирает следующий этап.

Каждая стадия и каждый execution-шаг выполняются в новом stateless LLM-turn: старый стек сообщений не передаётся. Следующий запрос заново собирается только из сохранённого `TaskState`. Поэтому даже после закрытия приложения revision получает исходную цель, план, результаты, лучшую текущую версию и замечания, но не скрытую историю прежней сессии.

## Запуск

```bash
cd ~/Dev/AI_Advent_Challenge/day-13
uv sync --locked
cp .env.example .env
```

Добавить `DEEPSEEK_API_KEY` в `.env`, затем:

Также добавить отдельный `OPENROUTER_API_KEY`. Модели стадий можно переопределить через `DEEPSEEK_MODEL`, `DEEPSEEK_REVISION_MODEL` и `OPENROUTER_VALIDATION_MODEL`, однако для воспроизводимого прогона рекомендуется оставить значения из `.env.example`.

```bash
uv run --locked python main.py
```

По умолчанию DeepSeek-вызовы используют `DEEPSEEK_MAX_TOKENS=1800`, а reasoning-валидатор — отдельный `OPENROUTER_VALIDATION_MAX_TOKENS=4000` и `reasoning.effort=low`. Execution ограничен инструкцией до 500 слов, а итог validation/revision — до 900 слов, чтобы отдельный stage-turn не обрывался на середине. Если API всё же вернёт `finish_reason=length`, checkpoint не продвинется: задача получит статус `failed`, а частичный ответ, usage и причина сохранятся в журнале для анализа. После увеличения лимита или уточнения профиля тот же этап можно повторить кнопкой `Запустить / повторить`.

Для planning запрос включает DeepSeek JSON mode (`response_format={"type":"json_object"}`). Validation использует OpenRouter Structured Outputs с `json_schema`, `strict=true` и `provider.require_parameters=true`; OpenRouter поэтому выбирает только совместимого провайдера. Validation-запрос не передаёт `temperature`, потому что закреплённая reasoning-модель не объявляет этот параметр. Непустые значения, минимум одно улучшение и правила переходов дополнительно проверяются приложением. `execution` и `revision` остаются обычными текстовыми ответами.

Для чистого прогона можно выбрать отдельное хранилище:

```bash
uv run --locked python main.py --data-dir /tmp/day-13-demo
```

Локальные состояния и диагностические журналы исключены из Git:

```text
data/
├── tasks/task-XX.json
└── runs/task-XX/events.jsonl
```

`task-XX.json` — текущий компактный checkpoint для продолжения. `events.jsonl` — append-only история всего прогона: каждое новое событие дописывается отдельной строкой и не перезаписывает прежние результаты.

## Диагностика прогона

Для каждого stage-turn журнал сохраняет:

- стадию, статус и шаг до и после вызова;
- фактический массив `messages` без HTTP-заголовков и API-ключа;
- полный ответ модели;
- входные, выходные и суммарные токены;
- длительность API-вызова;
- совершённый переход или безопасный текст ошибки;
- модель и workflow-профиль;
- `response_format`, `max_tokens` и фактический `finish_reason`.

Также записываются создание задачи, изменение цели или профиля, запрос паузы, фактическая пауза и продолжение. Поэтому первая validation не теряется после revision и может сравниваться с повторной.

Сводный отчёт по переходам, ошибкам, времени и токенам:

```bash
uv run --locked python report.py task-01
```

Для отдельного каталога данных:

```bash
uv run --locked python report.py task-01 --data-dir /tmp/day-13-demo
```

Полные prompts и ответы могут содержать пользовательские данные, поэтому журнал предназначен только для локального анализа и не добавляется в Git.

## Сценарий демонстрации

Кнопка `Автодемо · пауза` создаёт задачу с профилем `Объясняющий материал` и целью подготовить мини-гайд по безопасному началу работы с `asyncio`.

1. Агент выполняет planning и сохраняет три шага.
2. Выполняется первый execution-шаг.
3. Задача ставится на паузу; интерфейс показывает этап, шаг и действие `продолжить`.
4. Можно закрыть и заново запустить приложение: задача загрузится из JSON.
5. Кнопка `Продолжить` выполняет оставшиеся шаги и validation без нового ввода цели.
6. Если validation найдёт проблему, интерфейс покажет сохранённые замечания и до двух циклов revision → validation.

Интерфейс показывает цепочку из пяти стадий: план, выполнение, проверка, доработка и завершение, а над ней — явную карту моделей для стадий. Текущая стадия подсвечивается независимо от выбранной для просмотра; в технической панели указана фактически использованная модель. По каждой рабочей стадии можно открыть отдельный чат из всех сохранённых запросов и ответов; поэтому три execution-шага, две доработки и повторные validation-проверки не смешиваются и не теряются. Если доработка не понадобилась, она отмечается как пропущенная. Стадия `ЗАВЕРШЕНО` показывает итоговый результат, общий расход input/output/total tokens, число вызовов и время всего прогона.

До начала каждого API-вызова TUI немедленно показывает фактически отправляемый prompt, модель и незавершённую реплику `модель работает…`. После ответа эта реплика заменяется сохранённым результатом или конкретной ошибкой, поэтому длительный reasoning-вызов визуально не выглядит как зависание.

В итоговом API-прогоне агент без ошибок прошёл planning, три execution-шага, validation, одну доработку и повторную validation, после чего завершился со статусом `done`. Пауза и продолжение работают через сохранённый checkpoint: уже выполненные шаги повторно не запускаются, а цель не приходится объяснять заново.

Фактическая статистика прогона:

- 7 API-вызовов, 0 ошибок стадий;
- 14 606 input + 7 590 output = 22 196 токенов;
- 101,38 секунды суммарного API-времени;
- одна доработка из двух допустимых попыток.

Практический вывод: явный конечный автомат отделяет управление процессом от текста модели, а независимая validation-модель и ограниченный цикл revision позволяют повысить качество результата без риска бесконечной доработки. Append-only журнал сохраняет все промежуточные решения и расходы, поэтому поведение и стоимость прогона можно анализировать после завершения.
