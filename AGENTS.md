# Правила проекта для AI-агентов

Этот файл хранит устойчивые правила работы со всем репозиторием. Детали отдельных итераций фиксируются в `history.md`, а инструкции конкретного задания — в `day-XX/README.md`.

## Назначение проекта

- Этот репозиторий используется для изучения работы AI-агентов и практики их проектирования в рамках [AI Advent Challenge 9](https://mobiledeveloper.tech/ai_advent_9).
- Программа курса разбита по неделям и опубликована на странице челленджа. Локальные формулировки заданий и требования конкретного дня считать основным рабочим контекстом репозитория.
- Все задания находятся внутри этого репозитория: каждому дню соответствует отдельный каталог `day-XX`.

## Структура репозитория

- Использовать один репозиторий для всего AI Advent Challenge.
- Каждый день хранить в отдельном каталоге с именем `day-XX`.
- Код, зависимости и инструкции разных дней не смешивать без архитектурной необходимости.
- Каноническое описание задания, требования к сдаче и команды запуска хранить в `day-XX/README.md`.
- Файлы ДЗ, видео с результатом, вложения курса и другие связанные с заданием материалы, которые не должны попасть в Git, хранить только в `day-XX/resources/`.
- Файлы, необходимые для запуска решения, не помещать в игнорируемый `resources/`: хранить их рядом с кодом и коммитить явно.
- Перед изменениями изучать существующую структуру, похожие решения и `history.md`.
- После завершения содержательной итерации обновлять `history.md`: дата и время, что изменено, почему и какие проверки выполнены.

## Чаты

- Любое упоминание «чатов» без явно указанного другого источника означает локальные чаты только из каталога `./chats/` в корне текущего проекта.
- При поиске, чтении, создании и изменении чатов не выходить за пределы `./chats/` и не использовать внешние чаты, другие репозитории или пользовательские каталоги.
- Экспорты и рабочие файлы чатов считать локальными материалами: не добавлять их в Git, если пользователь явно не потребовал обратного.

## Python и uv

- Для Python использовать только `uv`: создание окружения, управление зависимостями, синхронизация и запуск команд.
- Каждый Python-день оформлять самостоятельным `uv`-проектом с собственными `pyproject.toml` и `uv.lock`.
- Добавлять и удалять зависимости командами `uv add` и `uv remove` из каталога соответствующего дня.
- Не редактировать `uv.lock` вручную; lock-файл обязательно хранить в Git.
- Запускать Python-код и проверки через `uv run`.
- Для первичной установки окружения использовать `uv sync`.
- Не создавать `requirements.txt`, не вызывать `pip` и не создавать окружение через `python -m venv`, если пользователь явно не запросил совместимость с этими инструментами.
- Каталог `.venv` всегда оставлять локальным и не добавлять в Git.

## Секреты

- API-ключи хранить только в локальных `.env` или системных переменных окружения.
- Добавлять в Git только безопасный `.env.example` без настоящих значений.
- Не читать и не выводить секреты в логи, консоль, документацию и ответы.

## Проверки

- Выполнять проверки через инструменты, принятые в конкретном дне.
- Не совершать платные или внешние API-вызовы без необходимости; если runtime-проверка не выполнялась, явно сообщать об этом.
- Не запускать браузерные и визуальные проверки без прямой просьбы пользователя.

## Публикация результатов

- При запросах «опубликуй видео с результатом», «опубликуй день»,
  «опубликуй ДЗ» и равнозначных формулировках обязательно использовать
  навык `publish-homework` из `.agents/skills/publish-homework/`.
- Активным днём считать день, над которым ведётся работа в текущей задаче.
  Если текущая задача и рабочий каталог не позволяют однозначно определить
  `day-XX`, уточнить день до внешних изменений.
- Не выбирать активный день только потому, что его номер является наибольшим в репозитории.
- Различать публикацию видео, публикацию дня и полную публикацию ДЗ. Выполнять только тот объём внешних изменений, который соответствует запросу пользователя; точные режимы и шаги определены в `publish-homework`.
- Запрос на публикацию разрешает предусмотренные выбранным режимом загрузку, коммит и push, но не разрешает публикацию посторонних изменений, force-push, переписывание истории или удаление удалённых файлов.
- Перед публикацией проверять фактические Git-ветку, upstream, remote, локальные изменения и настроенный файловый remote. Не публиковать молча в неожиданный репозиторий, ветку, каталог или под другим именем файла.
- Описание результата и выводы в README основывать только на сохранённых артефактах, логах и выполненных проверках. Не выдавать успешную команду загрузки или push за завершённую публикацию без проверки удалённого файла, публичной ссылки и удалённого коммита.
- Сохранять посторонние локальные изменения и добавлять в коммит только файлы активного дня и непосредственно связанную документацию.
