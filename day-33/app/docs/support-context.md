# Контекст поддержки тюнера Guitar Trainer: снимок v1 и передача через MCP

Этот документ описывает контракт диагностического снимка версии 1 (раздел 5) и
реализованную передачу контекста обращения через MCP (раздел 6). Снимок и его
передача — разные вещи: снимок собирается в браузере, а контекст обращения
получает backend через read-only MCP-инструмент, который читает SQLite;
ограниченный контекст передаётся DeepSeek.

## 1. Статус

**MCP-контекст реализован.** Локальный backend (`server/`) запускает дочерний
MCP-сервер (`server/mcp_server.py`) по stdio на официальном Python SDK (`mcp`),
реально проходит цикл `initialize` → `tools/list` → `tools/call` и через
read-only инструмент `get_ticket_context` получает контекст разрешённого
обращения. После MCP выполняется локальный retrieval E5-small на CPU только
по `docs/support/*.md`, затем DeepSeek Flash генерирует краткий русский ответ
в режиме без рассуждений. API использует JSON Output и серверную валидацию.
Корпус целиком не отправляется; звук обрабатывается локально в браузере,
не записывается и не передаётся. Подготовка embeddings — отдельная явная
операция; рабочий чат требует сети к DeepSeek и настроенного backend-ключа.

Локальный **чат поддержки реализован**: панель «Помощь»
(`web/src/support.js`) обращается к тому же loopback-origin — серверу
`server/` (FastAPI + SQLite, uv-проект). Текст сообщения, диагностический снимок
версии 1 и ответ AI сохраняются в локальной базе SQLite. Ответ и retrieval
v1 с копиями выбранных фрагментов сохраняются одной транзакцией; MCP-контекст
читается из сохранённых сообщений и снимков.

Диагностический снимок версии 1 (раздел 5) реализован локально: модуль
`web/src/diagnostics.js` хранит уже вычисленные приложением значения и по
запросу собирает JSON-совместимый объект. Снимок собирается **только в момент
отправки сообщения** через `collectSnapshot()` и прикладывается к сообщению;
в фоне он не собирается. Всё, что ниже отмечено как «требует реализации», —
несуществующее поведение; реализованное помечено явно. Передача контекста через
MCP, локальный retrieval и вызов DeepSeek описаны в разделе 6.

Сведения о текущем коде привязаны к фактической реализации `web/src/app.js`,
`web/src/capture.js`, `web/src/diagnostics.js`, `web/src/pitch.js`,
`web/src/display.js`.

## 2. Три разных понятия, которые нельзя смешивать

Для поддержки нужно различать три понятия. Все три реализованы локально;
снимок собирается в момент отправки сообщения и передаётся в локальный сервер
поддержки:

1. **Диагностический снимок** — то, что собирается при отправке сообщения в
   поддержку (раздел 5). Реализован локально (`web/src/diagnostics.js`); при
   отправке прикладывается к сообщению и сохраняется вместе с ним в SQLite
   (раздел 1). Внешним сервисам и моделям он не передаётся.
2. **Последние измерения аудиокадра** — значения, которые каждый кадр считает
   `web/src/capture.js` (`rmsOf`, `detectPitch`, `matchString`) и передаёт в
   `updateReading` (`web/src/capture.js:56-62`); последнее завершённое измерение
   сохраняет `web/src/diagnostics.js`. Это может быть значение текущего кадра
   или `null`.
3. **Удерживаемое показание интерфейса** — то, что видно на экране. Оно может
   быть старше последнего измерения: при тишине показание сохраняется бессрочно
   до следующего уверенного звука — ветка «Уже тишина»
   (`web/src/display.js:267-270`). Новый результат фиксирует `commit`
   (`web/src/display.js:157-166`), который записывает `state.lastUpdateAt`.
   `resetState` снимает показ при накопленном постороннем тоне или частой
   смене распознанных струн; это отдельное изменение интерфейса.

`state.lastUpdateAt` — время фиксации (`commit`) показания, а не момент
физического звука и не гарантия актуальности. Оно инициализируется `-Infinity`
(`web/src/display.js:177`), то есть до первого `commit` фиксации нет. Показ
может держаться долго и обновляется только при новом уверенном результате,
поэтому по `lastUpdateAt` нельзя судить, насколько свежим было измерение.
`resetState` не очищает `lastUpdateAt`: историческая фиксация может остаться,
хотя показ уже пуст. В контракте возраст фиксации передаётся только для
существующего показания; иначе он равен `null`. Для снимка введена отдельная
nullable-метка `state.committedAt`: она записывается в `commit` (в том числе при
повторной фиксации того же показания) и очищается при снятии показания
(см. раздел 5.3).

Отсюда важный вывод и для будущего снимка: **недавняя отправка снимка не
означает свежесть измерения.** Покадровый цикл мог замедлиться или прекратиться
(например, вкладка неактивна), а удерживаемое показание при этом остаётся на
экране. Снимок фиксирует состояние «как сейчас», а не доказывает, что измерения
продолжают поступать.

## 4. Ключевые различия

1. **Свежее измерение vs удерживаемое на экране показание.** При тишине (низкий
   уровень, отсутствие определённой высоты) показание сохраняется бессрочно до
   следующего уверенного звука — см. ветку «Уже тишина» (`web/src/display.js:267-270`).
   Последний `commit` (`web/src/display.js:157-166`) фиксирует показание,
   которое может сохраняться после длительной тишины. Его нельзя называть
   свежим измерением: возраст кадра и возраст показания различаются. Отдельного признака «устарело» в возвращаемом показании нет.
2. **Неизвестное значение vs отсутствие сигнала.** `detectPitch` возвращает
   `null` как при тишине (порог `RMS`, `web/src/pitch.js:53`), так и при
   неуверенном/шумовом сигнале (нет пика или пик ниже `MIN_CONFIDENCE`,
   `web/src/pitch.js:79`). В автомате отображения уровень используется для различения этих случаев:
   `hasSignal`/`isBelowFloor` (`web/src/display.js:90-102`) отличают пропуск
   детектора при значимом уровне от низкого уровня буфера; это правило
   обработки, а не независимая диагностика источника звука. Одиночный
   кадр без высоты не считается ни подтверждённой тишиной, ни новым щипком.
3. **Выбранное устройство vs фактический источник.** Выбора устройства в
   интерфейсе нет, `getUserMedia({ audio: true })` вызывается без `deviceId`
   (`web/src/app.js:46`); фактический источник (микрофон, выбранный браузером)
   кодом не запрашивается и не хранится. Понятия «выбранное устройство» в
   текущей реализации не существует.
4. **Внутренняя локальная переменная vs данные, доступные внешней интеграции.**
   `readingState`, `stream`, `context`, `buffer` живут внутри модулей
   (`web/src/app.js`, `web/src/capture.js`), а состояние внутри `display.js` —
   внутри `readingState`. Сами объекты наружу не публикуются и не отдаются: в
   `window`/`globalThis` ничего не выносится. Внешней интеграции доступна только
   точка доступа диагностики (`web/src/diagnostics.js`), которая возвращает
   JSON-совместимый снимок из примитивов и `null` по контракту версии 1; DOM
   остаётся отдельным представлением.

## 5. Минимальный контракт снимка (версия 1)

Нормативные определения полей ниже — контракт версии 1. Сбор снимка реализован
локально (`web/src/diagnostics.js`); отправка снимка в локальный сервер поддержки
и его сохранение в SQLite реализованы в рамках панели «Помощь». Передача
контекста обращения (включая сохранённый снимок) обработчику генерации через
MCP тоже реализована (раздел 6); снимок не входит в embedding-запрос.
Ограниченный контекст передаётся внешнему DeepSeek (раздел 1).

### 5.1 Поток данных

Поток реализован так:

1. **Guitar Trainer собирает снимок при отправке сообщения.** В момент отправки
   пользователем сообщения в поддержку страница формирует снимок текущего
   состояния (раздел 2, понятие 1).
2. **Сервер поддержки сохраняет снимок в контексте обращения.** Снимок
   прикладывается к обращению и хранится вместе с ним (разделы 6.4, `docs/support-api.md`).
3. **MCP-инструмент возвращает контекст обращения обработчику.** Backend читает
   сохранённый снимок и историю через read-only инструмент `get_ticket_context`
   и передаёт обработчику генерации (раздел 6).

При этом **браузеру не требуется самостоятельно говорить по MCP**: он только
отдаёт снимок в момент отправки сообщения; обращением и MCP-инструментом
управляет серверная сторона.

### 5.2 Время и возраст

`collectedAt` — календарное время сбора, строка UTC ISO 8601 в формате
`YYYY-MM-DDTHH:mm:ss.sssZ` (например, `2026-10-14T12:00:00.000Z`). Источник —
`new Date().toISOString()`. Это клиентские часы, без гарантии синхронизации
с сервером.

Для возраста используется **одна шкала локальных монотонных часов**:

1. После чтения и обработки буфера сохранить значения кадра вместе с
   `measuredAtMono = performance.now()`.
2. При фиксации нового показания сохранить отдельное
   `committedAtMono = performance.now()`; при снятии показания очистить эту
   метку. Нельзя определять фиксацию по изменению DOM: повторная фиксация
   может дать те же надписи.
3. При сборе один раз получить `collectedMono = performance.now()` и
   `collectedAt`; синхронно скопировать состояние. Возраст измерения равен
   `collectedMono - measuredAtMono`, возраст показания —
   `collectedMono - committedAtMono`. Это конечные неотрицательные числа в мс.
   Нет соответствующего события/показания — возраст `null`.

Это реализовано в версии 1: `web/src/capture.js` читает `performance.now()` один
раз за кадр, `updateReading` записывает `state.committedAt`, а
`web/src/diagnostics.js` считает возрасты из сохранённых `measuredAtMono` и
`committedAt`. `lastUpdateAt` в `display.js` остаётся исторической меткой и не
очищается `resetState`; для снимка используется отдельная `committedAt`,
которая очищается при снятии показания. `performance.now()` — монотонное время
страницы, не календарное.

Возраст описывает состояние **при сборе** и не включает последующую задержку
доставки. Недавние сбор/отправка не гарантируют свежесть измерения: цикл кадров
мог прекратиться или замедлиться. `requestAnimationFrame` обычно приостанавливается
в фоновых вкладках. Поведение монотонных часов при сне ОС различается между
реализациями; возраст — оценка по часам страницы, не гарантия физически
прошедшего времени после сна. Источники:
[Performance.now](https://developer.mozilla.org/en-US/docs/Web/API/Performance/now),
[requestAnimationFrame](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame).

### 5.3 Поля снимка

Все перечисленные поля и объекты-контейнеры обязательны в версии `1`.
Контейнеры `capture`, `audio`, `device`, `measurement`, `display`, `commit` —
JSON-объекты, не `null`; их смысл задаётся полями ниже. Числа должны быть
конечными: `NaN`, `Infinity` и `-Infinity` в JSON не передаются.

`null` не означает ноль. Для диагностических параметров это неизвестное или
не полученное значение; для результата алгоритма — не получена оценка, для
отображения — значение не показывается. Последние два случая уточняются
соседними полями, а не объявляются нулевым результатом.

Реализация версии 1 собирает поля ниже из состояния, которое ведёт
`web/src/diagnostics.js` по стадиям и результатам кадров
(`web/src/capture.js`). Значения санитизируются: неизвестное и `NaN`/±`Infinity`
дают `null`, а не ноль. Для версии 1 `device.actualLabel` всегда `null`:
метка фактической дорожки не собирается и эвристическое обезличивание не
применяется — это допустимое контрактом значение, а не изменение поля.

| `collectedAt` | строка | UTC ISO 8601, `YYYY-MM-DDTHH:mm:ss.sssZ` | запрещён | календарные часы клиента | `new Date().toISOString()` при сборе (`web/src/diagnostics.js`) |
| `capture.status` | строка или `null` | без единиц; `idle`, `requesting`, `initializing`, `capturing`, `error` | стадия неизвестна | стадии ведёт `web/src/capture.js` | `beginRequest`/`beginInitializing`/`beginCapturing`/`failCapture`; `capturing` не доказывает поступление данных |
| `capture.lastError` | строка или `null` | без единиц; `NotAllowedError`, `NotFoundError`, `NotReadableError`, `AbortError`, `InvalidStateError`, `SecurityError`, `TypeError`, `OverconstrainedError`, `other` | ошибка не получена/не сохранена; не доказательство успешной работы | `error.name` в `catch` запуска и кадра (`web/src/capture.js`) | белый список имён из контракта, неизвестное — `other`; очищается при новой попытке; `message`/`stack` не сохраняются |
| `audio.trackState` | строка или `null` | без единиц; `live`, `ended` | дорожка недоступна или состояние не проверено | `MediaStreamTrack.readyState`, ссылку хранит `web/src/diagnostics.js` | читается при сборе; `live` не доказывает наличие полезного звука |
| `audio.trackEnabled` | логическое или `null` | без единиц; `true`, `false` | дорожка недоступна или свойство не прочитано | `MediaStreamTrack.enabled` | читается при сборе; `false` отключает выход данных дорожки (для аудио получается тишина) |
| `audio.trackMuted` | логическое или `null` | без единиц; `true`, `false` | дорожка недоступна или свойство не прочитано | `MediaStreamTrack.muted` | читается при сборе; `true` — временная недоступность медиаданных, не пользовательский выбор микрофона |
| `audio.contextState` | строка или `null` | без единиц; `suspended`, `running`, `closed`, `interrupted` | AudioContext недоступен или состояние не прочитано | `AudioContext.state` | читается при сборе; состояние контекста не доказывает работоспособность источника |
| `device.actualLabel` | строка или `null` | без единиц; непустая обезличенная метка фактической дорожки, без постоянного ID | метка недоступна, пуста или не может быть безопасно обезличена | метка фактической дорожки (`stream.getAudioTracks()[0].label`), не выбранное в UI устройство | для версии 1 всегда `null`: метка не собирается и не обезличивается эвристически; `deviceId`/`groupId` не отправляются |
| `measurement.rms` | число или `null` | без единиц; конечное число ≥ 0, верхний предел 1 не предполагается | измерение не получено | `rmsOf` (`web/src/capture.js`), считается один раз за кадр | сохраняется последнее значение; `0` — нулевой уровень прочитанного буфера, не отсутствие измерения |
| `measurement.frequencyHz` | число или `null` | Гц; конечное число от 65 до 450 включительно | оценка частоты не получена | `detectPitch` (`web/src/pitch.js:40-107`) | сохраняется последнее значение; null после измерения не доказывает отсутствие сигнала |
| `measurement.matchedString` | строка или `null` | без единиц; `E2`, `A2`, `D3`, `G3`, `B3`, `E4` | сопоставление не получено | `matchString` (`web/src/pitch.js:113-131`) | сохраняется `match.string.name` либо null; это результат алгоритма, а не диагностика микрофона |
| `measurement.ageMs` | число или `null` | мс; конечное число ≥ 0 | кадр ещё не измерен / время неизвестно | `measuredAtMono = performance.now()` кадра (`web/src/capture.js`) | возраст считается по разделу 5.2; старое измерение сохраняет свой возраст |
| `display.string` | строка или `null` | без единиц; те же шесть имён струн | показание отсутствует | `reading.activeNote` из `updateReading` (`web/src/display.js`) | сохраняется последнее возвращённое reading, а не вычисляется из текущего measurement |
| `display.cents` | целое число или `null` | центы; целое от −100 до 100 включительно; при показе числа модуль ≥ 6 | число не показывается (метка «настроено» или пустой показ) | `labelsForCents` (`web/src/display.js:104-118`) | сохраняется `reading.cents`; null не означает точное отклонение 0 |
| `display.direction` | строка или `null` | без единиц; `Ослабить`, `Подтянуть` | направление не показывается | `reading.direction` | пустая строка нормализуется в null; направление относится к показанному числу |
| `display.tuned` | логическое | без единиц; `true`, `false` | запрещён; при пустом показе false | `reading.tuned` (`web/src/display.js`) | сохраняется флаг; true относится к зафиксированному показанию, не гарантирует текущую частоту |
| `commit.ageMs` | число или `null` | мс; конечное число ≥ 0 | нет текущего показания или неизвестно время его фиксации | `state.committedAt` (`web/src/display.js`), пишется в `commit`, очищается в `resetState` | возраст считается по разделу 5.2; `-Infinity` в снимок не попадает |

Значения `MediaStreamTrack` сверяются с
[readyState](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/readyState),
[enabled](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/enabled),
[muted](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/muted) и
[label](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/label).
Состояния контекста — с
[BaseAudioContext.state](https://developer.mozilla.org/en-US/docs/Web/API/BaseAudioContext/state).
Сведения, прочитанные из API дорожки, не подтверждают, что физический микрофон
исправен: источник может быть виртуальным, а label сохраняться после его
отсоединения. `getSettings()` описывает настройки фактической дорожки, но не
даёт её label; его `deviceId`/`groupId` в минимальный снимок не включаются:
[getSettings](https://developer.mozilla.org/en-US/docs/Web/API/MediaStreamTrack/getSettings).
RMS — амплитуда буфера, не дБ и не калиброванная громкость; сэмплы могут выходить
за номинальный диапазон −1…1:
[getFloatTimeDomainData](https://developer.mozilla.org/en-US/docs/Web/API/AnalyserNode/getFloatTimeDomainData).

Обязательная согласованность полей:

- Без измерения (`measurement.ageMs = null`) три значения measurement тоже
  null. При известном возрасте frequencyHz/matchedString могут быть null:
  кадр обработан, но частота/струна не найдены. `rms = 0` отличается от null.
- Шум и одновременно звучащие струны могут помешать распознаванию или дать
  неверный результат: detectPitch оценивает периодичность, не происхождение.
  Отсутствие сопоставления не означает отказ микрофона.
- При пустом показе display.string/cents/direction и commit.ageMs — null,
  display.tuned — false. При tuned=true число и направление — null; при
  показанном числе tuned=false, положительное число означает «Ослабить»,
  отрицательное — «Подтянуть».
- Метка «настроено» фиксируется по округлённой оценке внутри ±5 центов и может
  удерживаться при последующем сглаженном отклонении до 8 центов или в тишине.
  Она не доказывает, что последнее измерение лежит внутри ±5.
- В текущем коде `running = true` выставляется **до** getUserMedia и отражает
  попытку запуска, а не здоровье потока. Новую capture.status нельзя просто
  выводить из этого флага. Выбора устройства в интерфейсе сейчас нет.

### 5.4 Иллюстративные примеры JSON

Оба примера **иллюстративны**, не получены из реального захвата: они не
являются результатами проверки реального микрофона.

Пример (а): в предполагаемом сценарии захват работает, сигнал измерен 12 мс
назад. Показание зафиксировано раньше; измерение и показ — разные данные.

```json
{
  "schemaVersion": 1,
  "collectedAt": "2026-10-14T12:00:00.000Z",
  "capture": { "status": "capturing", "lastError": null },
  "audio": {
    "trackState": "live",
    "trackEnabled": true,
    "trackMuted": false,
    "contextState": "running"
  },
  "device": { "actualLabel": null },
  "measurement": {
    "rms": 0.083,
    "frequencyHz": 109.49,
    "matchedString": "A2",
    "ageMs": 12
  },
  "display": {
    "string": "A2",
    "cents": -8,
    "direction": "Подтянуть",
    "tuned": false
  },
  "commit": { "ageMs": 345 }
}
```

Пример (б): последняя попытка измерения не дала частоту или сопоставление;
контекст теперь suspended, новых кадров давно нет, на экране удерживается
старый результат. Capturing означает завершённую настройку захвата, а не
подтверждённую непрерывную работу потока.

```json
{
  "schemaVersion": 1,
  "collectedAt": "2026-10-14T12:05:30.000Z",
  "capture": { "status": "capturing", "lastError": null },
  "audio": {
    "trackState": "live",
    "trackEnabled": true,
    "trackMuted": false,
    "contextState": "suspended"
  },
  "device": { "actualLabel": null },
  "measurement": {
    "rms": 0,
    "frequencyHz": null,
    "matchedString": null,
    "ageMs": 8500
  },
  "display": {
    "string": "E2",
    "cents": null,
    "direction": null,
    "tuned": true
  },
  "commit": { "ageMs": 180000 }
}
```

В (б) `rms = 0` — измеренное значение старого буфера, не отсутствие данных
и не диагноз физического окружения. Если кадров ещё не было, вся группа
measurement содержала бы null. Свежая дата collectedAt не делает ни измерение,
ни показание свежими; null частоты не доказывает отсутствие сигнала, а скрытое
число при tuned=true не означает отклонение 0.

### 5.5 Ограничения снимка

- Снимок **не включает аудиобуферы** (сырые сэмплы не нужны и увеличивают объём
  и риск утечки).
- Снимок **не включает запись звука, персональные данные и постоянные
  идентификаторы устройств** без необходимости.
- Клиентский снимок **не является независимой проверкой оборудования**: он
  отражает то, что видит страница, а не состояние микрофона или звуковой
  подсистемы.
- В снимке **нет категорий вроде «сигнал слабый»**: такие оценки допустимы
  только вместе с явным правилом порога, которого сейчас нет.
- Снимок **не содержит ссылок на внутренние объекты** (`MediaStream`,
  `AudioContext`, `readingState`, аудиобуферы): реализация версии 1 отдаёт
  только примитивы и `null`.
- Для версии 1 `device.actualLabel` всегда `null`: метка фактической дорожки не
  собирается, эвристическое обезличивание не применяется.

### 5.6 Границы пользовательской базы знаний (реализовано)

Индексируются только непосредственные обычные Markdown-файлы `docs/support/*.md`.
Символические ссылки отклоняются. Технические документы (`docs/architecture.md`,
`README.md`, этот контракт), код, переписка, снимки, `tasks/` и `intakes/`
не входят в корпус. Путь задаётся сервером, пользователь не выбирает каталог.

## 6. Передача контекста через MCP и локальный поиск (реализовано)

Backend получает контекст через настоящий MCP, затем отдельно выполняет
retrieval. Обработчик готовит ограниченный payload, вызывает DeepSeek и проверяет ответ.

### 6.1 Инструмент и контракт результата

Единственный инструмент — read-only `get_ticket_context` без параметров
(`server/mcp_server.py`). Он возвращает объект:

| Поле | Смысл |
| --- | --- |
| `contextVersion` | версия контракта контекста; сейчас `1` |
| `conversationId` | идентификатор разрешённого обращения |
| `messageId` | идентификатор именно обрабатываемого сообщения |
| `snapshotSchemaVersion` | версия снимка; сейчас `1` |
| `snapshot` | объект снимка v1 обрабатываемого сообщения как есть |
| `snapshotReceivedAt` | `snapshots.created_at`: серверное время получения снимка, UTC ISO 8601 с миллисекундами (`YYYY-MM-DDTHH:mm:ss.sssZ`) |
| `history` | массив `{ id, role, text, state, createdAt, errorCode }` |
| `historyIncludedCount` | сколько сообщений вошло в историю |
| `historyTruncated` | была ли история усечена лимитами |
| `historyOmittedCount` | сколько более старых сообщений исключено |
| `limits` | `{ maxMessages, maxTextChars }`, действующие лимиты |

`snapshot` возвращается без пересчёта `measurement.ageMs`/`commit.ageMs` и без
усечения. `history` идёт в порядке возрастания серверного времени и
заканчивается обрабатываемым сообщением; `assistant` включается только при
`state=answered`, `user` в `state=error` — со своим явным `state`/`errorCode`.
Лимит истории совместный: по числу сообщений (`maxMessages`, по умолчанию 20) и
по суммарному объёму текста (`maxTextChars`, по умолчанию 16000) —
`server/config.py`. Отдельные сообщения не режутся посередине: при превышении
объёма более старые сообщения исключаются целиком, а факт усечения отражают
`historyTruncated`/`historyOmittedCount`. Текущий вопрос обязан войти целиком в
пределах `MAX_TEXT_LENGTH = 4000`; если он не помещается, инструмент возвращает
явную ошибку (`isError`), а не незаметно усекает текст.

### 6.2 Область доступа и пределы изоляции

- Область MCP-процесса (путь к БД, `conversationId`, `messageId`) задаётся
  доверенными параметрами запуска дочернего процесса после проверки владельца
  на HTTP-границе. Инструмент не принимает идентификаторы, SQL и файловые пути:
  передача их аргументами не расширяет область (аргументы игнорируются).
- Дочерний процесс **не получает cookie или токен браузерной сессии**. Он
  открывает БД в режиме только для чтения (`mode=ro`) и не копирует её ради
  каждого запроса (`server/db.py:open_readonly`).
- Отсутствие сообщения или снимка в разрешённой области (рассинхронизация,
  чужая область) — явная ошибка инструмента (`isError`), а не пустой или
  частичный успех.

**Предел изоляции.** Ограничение набора инструментов и read-only БД не является
полноценной изоляцией от вредоносного кода самого MCP-сервера: это код, который
backend запускает как собственный дочерний процесс. Изоляция здесь договорная
(какие инструменты и к каким данным), а не песочница.

### 6.3 Жизненный цикл и ошибки

- Один короткоживущий MCP-процесс на обработку сообщения, без пулов, демонов и
  фоновых сервисов.
- Ограниченный срок шагов и всей операции (`server/config.py`): initialize и
  tools/list — до 5 с, tools/call — до 10 с, вся операция — до 20 с.
- Проверяются ожидаемый инструмент и контракт ответа; обрабатываются `isError` и
  некорректный результат; ресурсы освобождаются, процесс завершается на успехе,
  ошибке, таймауте и остановке backend. Запуск идёт без shell и командной
  интерполяции, с минимальным окружением без облачных ключей.
- `stdout` дочернего процесса используется только для MCP-протокола; диагностика
  направляется в `stderr` без текстов сообщений, снимков и секретов. Полный
  контекст в технических логах не сохраняется.
- Любой сбой MCP (процесс не запустился, таймаут, `isError`, некорректный
  результат) не превращается в успех: публичный API отвечает HTTP-ошибкой с
  кодом `mcp_error` (502), сообщение пользователя остаётся сохранённым в
  `state=error`, успешный ответ не создаётся.

### 6.4 Как обработчик получает MCP-контекст и retrieval

Порядок: валидация сессии и запроса → сохранение сообщения и снимка →
завершение транзакции → настоящий MCP (`get_ticket_context`) → локальный поиск →
подготовка ограниченного messages → DeepSeek → строгая валидация → атомарное
сохранение ответа, retrieval и успешной попытки → HTTP-ответ. Прямого чтения
контекста в обход MCP и fallback нет. CPU-поиск выполняется отдельным worker
под глобальным допуском. При отмене/таймауте допуск удерживается до завершения
worker; его поздний результат не вызывает API. Модель загружается один раз на
процесс backend, под блокировкой и только на CPU.

System отделён от недоверенных JSON-данных: разрешённая история с текущим
вопросом ровно один раз, исходный snapshot и snapshotReceivedAt, до трёх целых
RAG-фрагментов. Служебные поля MCP, пути, cookie, секреты и similarity не входят
в payload. Неизвестные поля снимка отклоняются, а не передаются наружу.
История ограничивается 20 сообщениями/16000 символами, только целыми старыми
сообщениями; факт ограничения сохраняется. RAG — 12000 символов текста целых
фрагментов. Общий messages с system/JSON — 65536 UTF-8 байт. Инженерная оценка
всего входа/выхода E=4B+16384+1200 ≤ 1000000 не является точным токеновым
подсчётом. Обоснование ByteLevel BPE, неопределённость и запас приведены в README.
При превышении общего бюджета API не вызывается; снимок, вопрос и фрагмент
молча не обрезаются. Поисковый предел E5 512 токенов проверяется отдельно.

Ответ требует краткости, русского языка, разделения фактов, гипотез и
неизвестного, учёта выполненных действий и обоих возрастов measurement/commit.
Статусы running/capturing, frequencyHz=null и скрытые центы не служат
диагнозом. Нельзя выдумывать функции и объявлять проблему решённой; при
недостатке данных задаётся один полезный вопрос. Инструкции внутри данных
не получают системную роль. Эти правила — инструкция модели, а не гарантия
правильности каждого реального ответа: их оценивает человек в сценариях.

Модель возвращает только answer и sourceIds. Проверяются JSON, типы, ровно два
поля, непустой answer до 4000 символов, ID без дублей только из переданных
фрагментов и finish_reason=stop. Пустой sourceIds допустим. Некорректный ответ
отклоняется без исправляющего вызова, успешный assistant не создаётся.
Названия, цитаты и ссылки формирует сервер из сохранённого retrieval. Публичные
поля sources: id, title, headings, text, url. Старые кандидаты обозначаются
sourcesLegacy=true. HTML выводится через textContent; маршрут url показывает
сохранённый текст с проверкой владельца, без открытия произвольного файла.

Внутренний retrieval v1 хранит `version`, `indexFingerprint`, `queryText` и
`sources`: ID, статью, название, путь заголовков, дословный текст, символьные
координаты `[start, end)`, строки с единицы, `documentVersion` и `similarity`.
Сохранённый источник читается из базы переписки без актуального индекса;
доступ к истории и ответам предварительно проверяет владельца обращения.

### 6.5 Повтор после ошибки

Ошибка MCP, retrieval или DeepSeek сохраняет сообщение в `state=error`. Явный повтор с
тем же ключом идемпотентности запускает MCP и поиск по исходному сообщению и
снимку, без дубля. Успешная попытка фиксирует использованную версию индекса.
Завершённый ответ возвращается без перерасчёта. Каждая попытка сохраняет
историю до исходного messageId, время приёма снимка, индекс, retrieval,
переданные/выбранные ID, запрошенную/фактическую модель, время, длительность и
доступный nullable usage с cache-полями. На старте незавершённые попытки получают
interrupted с сохранением неопределённости внешнего исхода. Скрытых повторов нет.
Одна активная обработка без очереди; 10 начатых внешних попыток на сессию за час
по умолчанию, с сохранением расхода после рестарта. Полная классификация ошибок,
контракт хранения и конфигурация — в [API](support-api.md) и README.

Различаются `corpus_missing`/`corpus_invalid`, `model_missing`/
`model_incompatible`, `index_missing`/`index_stale`/`index_corrupt`/
`index_incompatible`, `query_too_long`, `mcp_error` и `retrieval_failed`.
Ошибка не превращается в пустой успешный ответ. При отсутствующей модели
нужен `prepare-model`, при проблемах индекса — `build-index`; слишком длинный
вопрос нужно сократить. В браузере доступен явный «Повторить».

### 6.6 Поисковый запрос, индекс и подготовка

Самостоятельный вопрос используется целиком. Короткое уточнение определяется
детерминированно: casefold, Unicode-слова по `[^\W_]+`, максимум 80 символов и
12 слов, точное совпадение последовательности слов с одной из фраз: «а теперь»,
«а дальше», «что дальше», «что ещё», «это уже пробовал», «это уже пробовала»,
«уже пробовал», «уже пробовала», «не помогло», «всё равно не работает».
Тогда берутся максимум два предыдущих user-сообщения из MCP, исключая текущее.
Текущий вопрос проверяется первым, затем целые сообщения от ближайшего, до
первого превышения бюджета. Итоговый порядок хронологический, разделитель —
две новые строки. Assistant и диагностический JSON не входят в запрос.

Полные входы с `query: ` / `passage: `, заголовками и специальными токенами
проверяются реальным токенизатором относительно 512 токенов, без усечения.
Ранжирование — скалярное произведение нормализованных векторов размерности 384,
при равенстве — ID. До трёх кандидатов без порога similarity; исключаются
одинаковые ID, дословно одинаковые тексты и пересечение координат одного
документа не менее 50% меньшего фрагмента. Кандидат не доказывает наличие ответа.

Отдельный SQLite-индекс содержит исходные фрагменты, embedding-текст, векторы и
манифест. Публикация атомарная; на старте и перед выдачей проверяются корпус,
параметры и отпечаток индекса. Смена версии во время поиска даёт явную ошибку.

Подготовка, закреплённая ревизия модели, allowlist файлов, каталоги, offline-запуск
и команды `prepare-model`, `build-index`, `evaluate --offline` описаны в
[README](../README.md#запуск-и-проверки), разбиение и манифест — в
[архитектуре](architecture.md). Результаты посредника отделены от обязательных
проверок контроллера; пользовательская приёмка остаётся отдельной.

Подготовку окружения и эксплуатационные команды `build-index` с записью в
`data/` выполняет посредник; обязательные проверки запускает контроллер.
Перед запуском приложения и проверок посредник задаёт
`PYTHONDONTWRITEBYTECODE=1`. Дочерний Python настоящего MCP дополнительно
запускается с `-B`, в том числе при явно заданном минимальном окружении.
Чтение корпуса открывает `docs`, `support` и статьи относительно дескриптора
корня проекта, запрещает символические ссылки на каждом уровне и сверяет
идентичность каталогов до и после чтения. Подмена каталога вызывает ошибку.


### 6.6 Тематика и недоверенные данные

Текущий текст, история пользователя и ассистента, снимок и фрагменты статей
остаются данными внутри одного user JSON; команды из них не меняют SYSTEM.
Строгая схема снимка не расширяется ради передачи произвольных инструкций.
История используется для продолжений вроде «Не помогло»: учитываются уже
предложенные действия, затем предлагается один следующий шаг или один вопрос.
Без достаточного контекста нужен один уточняющий вопрос, а не тематический отказ.

Поддержка охватывает фактические функции приложения, показания тюнера,
стандартный строй, настройку в пределах функций и необходимые проверки
микрофона, разрешений, системного источника звука и браузера. Отсутствие темы
в FAQ не исключает её из поддержки. Отсутствующие функции объясняются по
документации; широкий курс игры и общие задания не выполняются. Посторонний
запрос получает краткую границу с пустым sourceIds, смешанный — помощь только
с продуктовой частью. Роль сохраняется, системные инструкции не раскрываются.
Правила осторожной диагностики и различение текущего снимка и истории остаются
в силе. Кодовая валидация проверяет контракт, а эти правила задаются модели;
уместность ответа и источников требует отдельной содержательной оценки.


### 6.7 Сохранённый контекст сценариев T011

Инвентаризация JSON-свидетельств и результаты каждого сценария приведены в
[README](../README.md#границы-поддержки-guitar-trainer-t011). Одинаковые файлы
`/tmp/opencode/t011-evidence.json` и `data/tmp/t011-evidence.json` содержат метки
происхождения снимков, но не их значения. Фактические снимки, время приёма,
история и context_binding находятся в `/tmp/opencode/t011-acceptance.sqlite`,
прочитанной в режиме read-only. Данные синтетические, без физического микрофона.

Сценарий 2 привязан к сообщению 3: capturing, measurement.ageMs=25 мс,
commit.ageMs=60000 мс. Ответ объясняет удержание, но не сопоставляет эти
возрасты — замечание для содержательного ревью. Сценарий 5 (сообщение 9)
имеет error/NotAllowedError. Для сценария 6 (сообщение 13) привязаны historyIds
[9, 10, 11, 12, 13]: предыдущая пара сценария 5, отдельно подготовленная пара
user/assistant без генерации и текущая реплика. В подготовленном ответе уже
предложены разрешение для страницы, повторное включение и проверка localhost.
Текущий снимок шестого сценария — idle/lastError=null с отсутствующими
измерениями, а не повтор снимка ошибки. Сохранённый ответ просит статус и
адрес. Независимое ревью 2-009 подтвердило нарушение C6: два уточнения вместо
одного и внутренние имена полей вместо понятного описания состояния. Передача
истории не доказывает её содержательного учёта; C8 также ограничен. SYSTEM
уточнён для одного действия или одного вопроса об одном факте, с явной связью
с предложенными действиями и без предположения об их выполнении; действие
нельзя совмещать с вопросом, а список советов или проверок не считается одним
действием. Состояние следует объяснять обычными словами без имён полей.
Исторический ответ остаётся неуспешным по C6.

После корректировки выполнен один отдельно разрешённый пользователем вызов;
разрешение и предварительное объявление max_tokens=1200 подтверждены доверенным
ответом пользователя в контексте задачи. Повтор хранится в scenario6Retest,
а снимок и история — в `/tmp/opencode/t011-acceptance-retest.sqlite`.
В ней одна попытка (ID 1) для сообщения 3, ответ 4, historyIds=[1,2,3]:
подготовленная без генерации пара и «Не помогло». Текущий снимок содержит
error/NotAllowedError. Это изменённый контекст, а не воспроизведение исходного
idle-снимка и истории [9,10,11,12,13]. Исходный ответ сохранён независимо от
метки supersededBy.

В повторе предложены проверки блокировки и расширений и один вопрос об адресе
страницы с localhost, который уже предлагался в подготовленной истории.
Независимое ревью 2-019 подтвердило нарушение C6 также в повторе: несколько
проверок вместе с вопросом вместо одного действия либо уточнения; связь
с уже предложенными действиями не объяснена. Ограничение C8 и препятствие
технической готовности сохраняются. Явное правило SYSTEM и успешные
офлайн-проверки не устраняют наблюдаемого нарушения. В редакции 4 инструкция продолжения
ужесточена дополнительно: ровно одно из двух — одно следующее конкретное
действие либо один вопрос об одном недостающем факте; действие и вопрос
не совмещаются, а список советов или проверок не выдаётся за одно действие.
Пользователь разрешил не более двух новых вызовов только для сценария 6,
max_tokens=1200, без автоповторов; перепроверку выполняет посредник по
изолированному каналу. После ужесточения посредник выполнил один такой вызов
и сохранил его как scenario6Retest2: ответ содержит ровно один вопрос об одном
недостающем факте (какой текст показан в строке состояния), без списка советов
и без внутренних имён полей, sourceIds пуст. Это первый наблюдаемый ответ
сценария 6, удовлетворяющий правилу редакции 4, поэтому он фиксирует
фактический наблюдаемый исход C6; исходный ответ и первый повтор остаются
историческими неуспешными результатами. Один наблюдаемый пример не доказывает
устойчивое поведение модели.
Значения снимков остаются в изолированных БД, не в JSON.
Всего наблюдаются восемь попыток, сопоставляемых по БД и ID; модели, retrieval,
индекс и usage записаны, журналы содержат шесть, один и один POST сообщений.
Для второго повтора отдельный путь изолированной БД в материалах не указан, а
полная трассировка исторических звеньев и учёт вызовов за пределами материалов
недоступны. Достаточность для C7 и техническую готовность оценивает независимое
ревью. Подробные результаты и актуальный хеш — в README. На этом рабочем этапе
новых внешних вызовов не выполнялось; проверки текущего дерева выполняет контроллер,
пользовательская приёмка ожидается.
